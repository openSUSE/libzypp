# 00a – Concepts Primer and Glossary

This chapter is the vocabulary primer for the rest of the handbook. It explains every important package-management and
libzypp concept from first principles: what it is, why it exists, how libzypp models it (classes and files), a small
example, the main gotcha, and where the details are. Part A is a narrative grouped by topic. Part B is an alphabetical
glossary (terms, abbreviations, bug-tracker prefixes) with code anchors and chapter links.

All paths are relative to `libzypp/`. Remember that many "legacy" classes physically live in `zypp-logic/` (see
[00](00-big-picture.md) and [01](01-layout-build-and-dependencies.md)); the include path `<zypp/Foo.h>` does not tell
you which directory holds the file.

How each concept is laid out:

> **What** – definition · **Why** – the problem it solves · **In libzypp** – classes/files ·
> **Example** · **Gotcha** · **See** – chapter with depth

# Part A – Conceptual primer

## A.1 Packages and identity

### rpm package

* **What**: a file (`foo-1.2-3.1.x86_64.rpm`) with a payload (files), scriptlets (`%pre`, `%post`, `%posttrans`, …),
  a header with metadata (name, version, dependencies, changelog, signatures).
* **Why**: rpm is the installer. libzypp never unpacks rpms itself. It decides *what* to install, downloads it,
  checks signatures, and hands it to rpm (directly via `rpm` calls or via the `zypp-rpm` helper).
* **In libzypp**: a `sat::Solvable` of kind `package`, wrapped by `Package` (`zypp/zypp/Package.h`); rpm access in
  `zypp/zypp/target/rpm/`.
* **Gotcha**: most package attributes come from **repo metadata**, not from the rpm. Support keywords and the
  "retracted" marker exist only in repo metadata; the changelog only for installed packages.
* **See**: [03 §16.4](03-sat-pool-and-resolvables.md#164-package-zyppzypppackagehcc-srcpackage-application),
  [08 §1](08-target-commit-and-rpm.md#1-big-picture).

### NEVRA (Name, Epoch, Version, Release, Arch)

* **What**: the full identity of an rpm: `name-[epoch:]version-release.arch`, e.g. `bash-5.2.37-1.1.x86_64`.
* **Why**: name alone is ambiguous (several versions, several archs in a pool). NEVRA is how humans and tools name an
  exact build.
* **In libzypp**: the term is not used in headers; the parts are `Solvable::name()`, `edition()` (E-V-R),
  `arch()`. zypper uses NEVRA strings for requests ([04 §15.2](04-solver.md#152-zypper-locked-items-become-requiresconflicts)).
* **Gotcha**: two solvables with identical NEVRA can still differ (vendor, buildtime, repo). "Same package" checks use
  `Solvable::identical()`, not a NEVRA compare.

### Edition (`[epoch:]version[-release]`)

* **What**: the "EVR" part. `epoch` is an integer override (rarely used), `version` is upstream's version, `release`
  is the distribution build counter.
* **Why**: deciding "newer/older" needs rpm's exact comparison rules, and dependency matching (`foo >= 1.2`) needs a
  wildcard-aware variant.
* **In libzypp**: `Edition` (`zypp-logic/zypp/Edition.{h,cc}`): `compare`/`operator<` is a strict order for sorting;
  `match` treats an empty version or release as wildcard (for capability matching).
* **Example**: `Edition("1.0-1") < Edition("1:0.9-1")` (epoch wins); `1.a < 1.0`; `1.0 == 1_0`.
* **Gotcha**: **`match` is not transitive** – never order a container by it.
* **See**: [03 §4.1](03-sat-pool-and-resolvables.md#41-edition--rel--range).

### Arch, compatible archs, noarch

* **What**: the CPU architecture a package is built for (`x86_64`, `aarch64`, `i586`, …). `noarch` packages (scripts,
  data) run anywhere. An arch is *compatible* with a system if the system can run it.
* **Why**: a pool may hold packages for many archs (multilib, foreign repos). The system can only install compatible
  ones and should prefer the "best" one.
* **In libzypp**: `Arch` (`zypp-logic/zypp/Arch.{h,cc}`) with a compat table; the system arch comes from
  `ZConfig::systemArchitecture()`.
* **Gotcha**: when a repo is loaded, **solvables of incompatible arch are deleted from the pool**. Changing the arch
  later requires reloading the repos.
* **See**: [03 §4.2](03-sat-pool-and-resolvables.md#42-arch), [09 §6](09-configuration-and-environment.md#6-architecture-detection).

### Vendor

* **What**: the string identifying who built a package (`SUSE LLC <https://www.suse.com/>`, `openSUSE`,
  `obs://build.opensuse.org/home:foo`).
* **Why**: replacing a SUSE build with a third-party build (or vice versa) during an update is risky. Vendor
  stickiness prevents silent vendor switches.
* **In libzypp**: `Solvable::vendor()`; equivalence classes in `VendorAttr` read from `/etc/zypp/vendors.d/*`. See
  [vendor stickiness](#vendor-stickiness-and-vendor-equivalence).
* **Gotcha**: matching is case-insensitive **longest prefix**, with special rules for `opensuse*` vendors.
* **See**: [03 §10](03-sat-pool-and-resolvables.md#vendorattr).

### Ident and kind prefixes

* **What**: the *ident* is libsolv's "name" of a solvable, which carries the kind as a prefix for non-packages:
  `foo` (package), `patch:openSUSE-2024-123`, `pattern:base`, `product:SLES`, `application:org.gnome.Gedit`.
* **Why**: libsolv has one flat name space. Prefixing lets a package and a pattern both be called `base`.
* **In libzypp**: `ResKind` (`zypp-logic/zypp/ResKind.{h,cc}`); `ResKind::satIdent(kind, name)` builds idents,
  `Solvable::ident()`/`kind()`/`name()` split them.
* **Example**: `ResKind::satIdent(ResKind::pattern, "base") == "pattern:base"`; `Solvable::name()` of that solvable is
  `base`.
* **Gotcha**: source packages have **no prefix** – they are identified by arch `src`/`nosrc` and share the ident with
  the binary package.
* **See**: [03 §4.3](03-sat-pool-and-resolvables.md#43-reskind-and-kind-prefixes).

## A.2 The layered object model

### IdString and the string pool

* **What**: an `int` handle to a string interned in libsolv's string pool.
* **Why**: millions of names, versions and dependency strings repeat. Interning makes them cheap to copy and compare
  (equality = integer compare) and is how libsolv works internally.
* **In libzypp**: `IdString` (`zypp-logic/zypp/IdString.{h,cc}`) and the `IdStringType<Derived>` helper used by
  `Edition`, `ResKind`, `Locale`, ….
* **Gotcha**: ids are only valid inside this process and pool – **never persist raw ids**.
* **See**: [03 §3](03-sat-pool-and-resolvables.md#3-string-pooling-idstring-and-idstringtype).

### Solvable → Resolvable/ResObject → PoolItem → Selectable

The most confusing part for newcomers is that one package is represented by up to five different objects. They are
layers, each adding something:

```
  libsolv ::Solvable      owned by libsolv
        ▼
  sat::Solvable           value handle (just the id); all data lookups
        ▼
  ResObject & subclasses  typed, stateless API (Package, Patch, Product, …)
        ▼
  PoolItem                + ResStatus = "a solvable plus its status"
        ▼
  ui::Selectable          all items of one (kind, name), candidate, ui::Status
```

* **Why so many**: `sat::Solvable` is the libsolv view (data); `ResObject` is a friendlier typed API; `PoolItem` adds the
  mutable *transaction state* the application and solver negotiate; `Selectable` is the "one row per package name" UI
  view.
* **Example**:
  ```cpp
  sat::Solvable s = …;                         // e.g. from WhatProvides
  PoolItem pi( s );                            // look up the PoolItem (O(1), index = solvable id)
  Package::constPtr p = pi->asKind<Package>(); // ResObject subclass
  ui::Selectable::Ptr sel = ui::Selectable::get( pi );   // the per-name group
  pi.status().setToBeInstalled( ResStatus::USER );
  ```
* **Gotcha**: `Resolvable` here means "the C++ base class". In everyday talk, "resolvable" means "anything the solver
  handles" (package, patch, …).
* **See**: [03c §1](03c-respool-and-selectables.md#1-the-three-layers-and-who-uses-which),
  [03 §6](03-sat-pool-and-resolvables.md#6-satsolvable-and-friends), [03 §8](03-sat-pool-and-resolvables.md#8-resolvable-object-hierarchy).

### Serial numbers and stale handles

* **What**: `sat::Pool::serial()` changes whenever the pool content changes (repo added/removed);
  `sat::Pool::serialIDs()` changes when solvable ids are *reused*.
* **Why**: all derived layers (`ResPool` store, Selectables, whatprovides, caches) are rebuilt lazily. They watch the
  serials to know when.
* **Gotcha**: holding `PoolItem`s, `Selectable`s or a `ResPoolProxy` across a repo reload keeps **stale objects** alive;
  status changes on them no longer affect the pool.
* **See**: [03 §5.2](03-sat-pool-and-resolvables.md#52-serial-numbers-and-lazy-housekeeping),
  [03c §6](03c-respool-and-selectables.md#6-lifecycle-and-invalidation).

## A.3 Dependencies

### Capability

* **What**: one dependency expression: `foo`, `foo >= 1.2`, `libc.so.6()(64bit)`, `/usr/bin/perl`,
  `(python3 or python311)`, `namespace:language(de)`.
* **Why**: packages do not depend on packages, they depend on *capabilities* that other packages *provide*. That gives
  alternatives, virtual provides, file deps, renames.
* **In libzypp**: `Capability` (`zypp/zypp/Capability.{h,cc}`) is just a libsolv dependency `Id`; `CapDetail` splits
  it; `Capabilities` is a solvable's dependency array.
* **Example**: `Capability("foo >= 1.2")`, `Capability("foo", Rel::GE, Edition("1.2"))`, `Capability("(a and b)")`.
* **Gotcha**: string parsing is lenient – anything it can't parse becomes a NAMED capability.
* **See**: [03 §4.4](03-sat-pool-and-resolvables.md#44-capability-capdetail-capabilities).

### Dependency types

`Dep` (`zypp-logic/zypp/Dep.h`): hard `REQUIRES` / `PREREQUIRES` / `CONFLICTS` / `OBSOLETES`, the `PROVIDES` side,
and weak `RECOMMENDS` / `SUPPLEMENTS` (reverse recommends) / `SUGGESTS` / `ENHANCES` (UI hints only).

* **Gotcha**: `dep_requires()` contains **both** requires and prerequires. Weak deps are followed unless
  [onlyRequires](#recommends-supplements-and-onlyrequires) is active, and even then namespace ones are followed.
* **See**: [03 §6](03-sat-pool-and-resolvables.md#6-satsolvable-and-friends).

### Versioned and rich (boolean) dependencies

* **What**: versioned = `name op edition`. Rich deps (rpm ≥ 4.13) = boolean expressions `(a and b)`, `(a or b)`,
  `(a if b else c)`, `(a unless b)`, `(a with b)`, `(a without b)`.
* **In libzypp**: `CapDetail::EXPRESSION`; libzypp does not evaluate them – libsolv does.
* **See**: [04 §18.3](04-solver.md#183-packageand-and-rich-boolean-deps).

### Namespaces (language, modalias, filesystem)

* **What**: special capabilities `namespace:NAME(value)` whose truth is decided by a callback into libzypp at solve
  time instead of by a provider package.
* **Why**: "install the German translation of every installed package", "install the driver for this PCI device",
  "install btrfs tools if a btrfs filesystem is used" – facts about the *system*, not about packages.
* **In libzypp**: `ResolverNamespace`, answered by `sat::detail::PoolImpl::nsCallback`.
* **Example**: `-lang` packages carry `Provides: locale(foo:de;fr)`, which libsolv turns into
  `Supplements: (foo and (namespace:language(de) or namespace:language(fr)))`.
* **Gotcha**: libsolv caches namespace answers; changing their inputs (e.g. requested locales) must call `depSetDirty()`.
* **See**: mechanism [03 §9](03-sat-pool-and-resolvables.md#9-namespaces-language-modalias-filesystem), solver behaviour
  [04 §18.2](04-solver.md#182-language-and-modalias-packages), modalias [03b](03b-modalias.md).

### WhatProvides

* **What**: the list of solvables providing a capability (`sat::WhatProvides(cap)`, `zypp/zypp/sat/WhatProvides.h`).
* **Gotcha**: it calls `sat::Pool::prepare()` first, which may rebuild libsolv's index – expensive after pool changes.
* **See**: [03 §6](03-sat-pool-and-resolvables.md#6-satsolvable-and-friends).

### `packageand()` and other legacy SUSE dependency syntax

* **What**: pre-rich-dep SUSE syntax in `Supplements`: `packageand(a:b)` = "a and b", `modalias(...)`,
  `language(...)`, `filesystem(...)`, and `foo:/path` "split provides".
* **In libzypp**: none – libsolv rewrites them at parse time into rich deps / `namespace:…`.
* **See**: [04 §18.3](04-solver.md#183-packageand-and-rich-boolean-deps).

## A.4 Resolvable kinds

> **Deep dive:** [03a – Special solvables](03a-special-solvables.md) covers how each of these kinds is *defined* in metadata, how libsolv converts it, and its quirks.

### package and srcpackage

* **package**: a binary rpm (`Package`).
* **srcpackage**: a source rpm (`.src.rpm`/`.nosrc.rpm`, `SrcPackage`). Only installable via `zypper source-install`;
  the solver ignores them unless `Resolver::setSolveSrcPackages(true)`.
* **Gotcha**: support level keywords only exist in repo metadata; an installed package inherits them from an identical
  available copy.
* **See**: [03 §16.4](03-sat-pool-and-resolvables.md#164-package-zyppzypppackagehcc-srcpackage-application),
  [03a §A5](03a-special-solvables.md#a5-source-packages).

### patch

* **What**: an update advisory from `updateinfo.xml` (`patch:openSUSE-SLE-15.6-2024-1234`): a set of fixed package
  versions plus category, severity, references (bugzilla/CVE), message, flags.
* **Why**: customers apply *fixes* ("all security patches"), not arbitrary newest packages. Patches also carry
  reboot/restart/interactive hints.
* **In libzypp**: `Patch` (`zypp/zypp/Patch.{h,cc}`). libsolv turns each `<package>` entry into a **conflict**
  `name.arch < evr`, so "installing" a patch means "no installed package may be older than the fixed version".
* **Gotcha**: patches are **pseudo-installed** – never in the rpmdb; their status (needed / satisfied / broken) comes
  from the solver's establish pass.
* **See**: [03a §B.1](03a-special-solvables.md#b1-patches-the-metadata), [03 §16.1](03-sat-pool-and-resolvables.md#161-patch-zyppzypppatchhcc),
  [04 §19](04-solver.md#19-patches-from-libsolvs-point-of-view).

### pattern

* **What**: a named group of packages for a use case (`pattern:kde`, `pattern:devel_C_C++`), shown in installers.
* **Why**: users pick "a KDE desktop", not 800 packages.
* **In libzypp**: `Pattern` (`zypp/zypp/Pattern.{h,cc}`). Patterns are backed by real **pattern packages**
  (`patterns-*` rpms providing `pattern() = name`) from which libsolv generates the `pattern:` solvable (autopattern).
* **Gotcha**: `--no-recommends` also drops recommended pattern members.
* **See**: [03a §A3](03a-special-solvables.md#a3-patterns), [03 §16.2](03-sat-pool-and-resolvables.md#162-pattern-zyppzypppatternhcc).

### product

* **What**: a distribution or extension/module the system is "running" (`product:SLES`, `product:sle-module-basesystem`,
  `product:openSUSE`). Each product has a **release package** (e.g. `sles-release`) that installs an XML **product
  file** to `/etc/products.d/<name>.prod`.
* **Why**: registration, support status, upgrade paths, `$releasever`, which repos update what, end of life.
* **In libzypp**: `Product` (`zypp/zypp/Product.{h,cc}`); the release package is `Product::referencePackage()` and
  becomes the product's [buddy](#a5-buddy--all-meanings); the base product is the one `/etc/products.d/baseproduct`
  points to.
* **Gotcha**: product and release package **share one `ResStatus`**, so locking one locks both.
* **See**: [03a §A2](03a-special-solvables.md#a2-products), [03 §16.3](03-sat-pool-and-resolvables.md#163-product-zyppzyppproducthcc),
  [08 §13](08-target-commit-and-rpm.md#13-products-on-the-target-etcproductsd-baseproduct-releasever).

### application

* **What**: an AppStream/appdata component (`application:org.gnome.Gedit`) for software centres.
* **In libzypp**: `Application`, generated by libsolv's `repo_add_appdata`; no accessors beyond `ResObject`.
  Not to be confused with **appdata plugins**, run by `~RepoManager` after repo changes.
* **See**: [03a §A4](03a-special-solvables.md#a4-applications-dead-kind), [05 §4.2](05-repositories-and-services.md#42-destructor-appdata-plugins).

## A.5 "Buddy" – all meanings

"Buddy" is used for **three unrelated things** in the code. Always check which one a comment or bug report means.

### (a) PoolItem buddy: product ↔ release package (shared `ResStatus`)

* **What**: a `PoolItem` can use another item's `ResStatus` object. Used for every `Product` and its
  `referencePackage()` (the `-release` rpm).
* **Why**: a product is not an rpm; you install/remove it by installing/removing its release package. Sharing the
  status makes "select product" and "select release package" the same action.
* **In libzypp**: `PoolItem::buddy()` / private `setBuddy()`, set by `pool::PoolImpl::store()` for new products
  (successor of bnc#466565; libsolv side: the link rule,
  [03a §A1.1](03a-special-solvables.md#a11-linked-packages-the-common-mechanism-behind-products-patterns-and-applications)).
  Encoding: `_buddy > 0` = "use the buddy's status"; `< 0` = "my status is used by `-_buddy`". Second-level buddies
  are refused (ERR log).
* **Consequences**: locks match an item *or its buddy* (bsc#1225267); `Product::replacedProducts()`/`droplist()` read
  the buddy's deps; commit skips non-package items that have a buddy.
* **Gotcha**: products without a release package have no buddy – they log `WAR ... no reference package found` and
  behave independently.
* **See**: [03c §3.6](03c-respool-and-selectables.md#36-the-buddy).

### (b) Buddy keys: GPG keys from repo keyhints

* **What**: extra public keys announced in `repomd.xml` as `<keyword>gpg-pubkey-…</keyword>` (**keyhints**). They are
  downloaded into the *general* keyring and remembered as "buddies" of the signing key.
* **Why**: a repo can announce the keys it will use for packages (or its next key). If the metadata is signed by a key
  the user already **trusts**, the buddies are imported as trusted automatically, without asking.
* **In libzypp**: `VerifyFileContext::buddyKeys()` (`zypp/zypp/KeyRingContexts.{h,cc}`); imported only if the file
  is validated **and** the signing key is trusted.
* **Gotcha**: keyhints are untrusted input; their file names and ids were hardened (bsc#1267426, bsc#1271730).
* **See**: [06 §13](06-security-gpg-keyring.md#13-keyhint-hardening-bsc1267426--cve-2026-44941-bsc1271730).

### (c) Buddy mapping in the solver and in `sat::Transaction`

* **SATResolver `mapBuddy` / `mapItem` / `mapSolvable`** (`zypp/zypp/solver/detail/SATResolver.cc` ~l.1074): when
  building problem texts, a **package** that has a buddy is replaced by the buddy (the product), so the user reads
  "product foo conflicts with product bar" instead of "package foo-release conflicts with …". Only packages map to
  buddies, never vice versa.
* **`sat::Transaction` `_linkMap`** (`zypp/zypp/sat/Transaction.cc`): non-package steps with a buddy follow the
  buddy's step stage (`STEP_DONE`/`STEP_ERROR`), because they share the status.

No other meanings of "buddy" were found (`grep -rni buddy zypp zypp-logic zyppng`).

## A.6 Repositories and services

### Repository (repo)

* **What**: a source of packages plus metadata describing them (an HTTP directory, a DVD, an ISO, a local dir).
* **Why**: the solver needs to know *all* available packages and their dependencies without downloading rpms.
* **In libzypp** – don't mix up `RepoInfo` (the **configuration**, one `[alias]` section of a `.repo` file),
  `Repository` (the **loaded** repo in the sat pool) and `RepoManager` (add/remove/refresh/build cache/load).
* **Gotcha**: `RepoManager` methods only change files and caches. To use a repo you must `loadFromCache()` it into the pool.
* **See**: [05 §3](05-repositories-and-services.md#3-repoinfobase-repoinfo-serviceinfo),
  [05 §4](05-repositories-and-services.md#4-repomanager-lifecycle).

### Alias vs name

* **alias**: the unique, stable id (`[repo-oss]`), used as file name, cache dir name and in history/locks/testcases.
* **name**: free-text label (may contain repo variables).
* **Gotcha**: service repos get the alias `<service>:<alias>`.
* **See**: [05 §3.1](05-repositories-and-services.md#31-repoinfobase-zyppzyppreporepoinfobasehcc).

### baseurl, mirrorlist, metalink

* **baseurl**: one or more URLs where the repo lives. **mirrorlist** / **metalink**: a URL returning a list of
  mirrors.
* **Gotcha**: baseurls are *authorities*, mirrors are just extra endpoints. Security relevant files (repomd.xml, keys,
  signatures) are only fetched from authorities.
* **See**: [05 §11](05-repositories-and-services.md#11-repomirrorlist-in-depth-zyppzyppreporepomirrorlisthcc),
  [07 §7.5](07-media-and-downloads.md#75-mirrors-in-the-media-layer-mirroredorigin).

### Repo type and master index

* **Types** (`RepoType`): `rpm-md` (master index `repodata/repomd.xml`), `yast2`/susetags (`content`), `plaindir`
  (a directory of rpms, no index).
* **Master index**: the one small file that references (by checksum) all other metadata files. It is what gets GPG-signed.
  Its signature transitively secures everything else.
* **Gotcha**: `type=` in `.repo` files is **ignored on read** – RepoManager probes.
* **See**: [05 §5.4–5.5](05-repositories-and-services.md#55-probing-proberepologic),
  [05 §12](05-repositories-and-services.md#12-metadata-and-config-parsers-who-parses-what).

### Raw cache vs solv cache

```
download ─► /var/cache/zypp/raw/<alias>/      raw metadata as on the server
repo2solv ─► /var/cache/zypp/solv/<alias>/solv libsolv binary file
loadFromCache ─► sat::Pool::addRepoSolv()
```

* **Why two**: parsing XML is slow; libsolv's `.solv` loads in milliseconds. The raw cache is kept so the solv can be
  rebuilt (e.g. after a libsolv update) without network.
* **Gotcha**: a solv file built by a different libsolv tool version is rebuilt automatically.
* **See**: [05 §2.3](05-repositories-and-services.md#23-on-disk-layout), [05 §5.6](05-repositories-and-services.md#56-building-the-solv-cache-buildcachelogic).

### The `@System` repo

* **What**: the pseudo-repository holding the **installed** packages, built from the rpm database (plus
  `/etc/products.d`) by `rpmdb2solv`. libsolv knows it as the "installed" repo.
* **In libzypp**: `sat::Pool::systemRepo()`, `Solvable::isSystem()`; rebuilt when the rpmdb cookie changes.
* **Gotcha**: repo-only data (support keywords, retracted marker) is matched to installed packages by identity.
* **See**: [03 §5.3](03-sat-pool-and-resolvables.md#53-system-and-how-the-pool-is-filled),
  [08 §3](08-target-commit-and-rpm.md#3-target-initialisation-rpmdb-and-the-system-cache).

### Priority, autorefresh, keeppackages, enabled

* Per-repo settings: `priority` (default 99, 1 = highest), `enabled`, `autorefresh` (rate-limited by
  `repo.refresh.delay`), `keeppackages` (keep downloaded rpms).
* **Gotcha**: priority beats version: a newer package in a priority-99 repo loses against an older one in priority 90
  for new installs/updates (that is the purpose).
* **See**: [05 §3.2–3.3](05-repositories-and-services.md#33-repoinfo-semantics-worth-knowing-zyppzypprepoinfocc).

### Repo variables

* **What**: `$arch`, `$basearch`, `$releasever`, … plus custom variables from `/etc/zypp/vars.d/<name>`, usable in
  URLs and names.
* **In libzypp**: `zypp/zypp/repo/RepoVariables.{h,cc}`.
* **Gotcha**: config writers must use the `raw*()` getters, or the expanded value gets saved.
* **See**: [05 §6](05-repositories-and-services.md#6-repo-variables-zyppzyppreporepovariableshcc).

### RepoStatus and cookies

* **What**: a fingerprint (checksum + timestamp) of metadata, stored in `cookie` files.
* **Why**: decides "do I need to refresh/rebuild?" by comparing the server's master index status with the raw cache, and
  the raw cache status with the solv cache.
* **Gotcha**: the status includes the repo URL, so changing the URL forces a refresh.
* **See**: [05 §5.3](05-repositories-and-services.md#53-repostatus-and-cookie-files-zyppzypprepostatushcc).

### Services (RIS, plugin services)

* **What**: a *service* is a URL or script that manages a **list of repositories**. RepoManager refreshes the service
  and adds/removes/modifies the repos it lists.
* **Why**: SUSE registration (SCC/RMT/SMT) gives each system a personalized set of repos with credentials; the service
  keeps that set up to date when modules are added or products upgraded.
* **In libzypp**: `ServiceInfo`, files in `/etc/zypp/services.d/*.service`; types **RIS** (`repoindex.xml`) and
  **PLUGIN** (an executable printing a `.repo` file).
* **Gotcha**: changing a service's enabled state cascades to all its repos.
* **See**: [05 §7](05-repositories-and-services.md#7-services).

## A.7 Pool and status

### sat::Pool vs ResPool

`sat::Pool` wraps the libsolv pool (data only: solvables, repos, whatprovides); `ResPool` is the `PoolItem` store on
top (adds `ResStatus`, locks, established states). Both are handles to process-wide singletons; there is exactly
**one** libsolv pool per process. See [03 §2](03-sat-pool-and-resolvables.md#2-one-libsolv-pool-two-owners),
[03c §2](03c-respool-and-selectables.md#2-respool).

### ResStatus

* **What**: a 16-bit bitfield per `PoolItem` (`zypp/zypp/ResStatus.h`): installed or not, **Transact**
  (`KEEP_STATE` / `LOCKED` / `TRANSACT`), the causer, patch validation, weak bits, ….
* **Why**: the application, the UI and the solver all edit the same "what will happen" state. The bitfield records
  *what* should happen and *who* asked for it.
* **Example**: `isToBeInstalled() = uninstalled && TRANSACT`.
* **See**: [03 §7.3](03-sat-pool-and-resolvables.md#73-resstatus-bit-layout).

### Causer levels (USER, APPL_HIGH, APPL_LOW, SOLVER)

* **What**: `ResStatus::TransactByValue`, ordered `SOLVER < APPL_LOW < APPL_HIGH < USER`.
* **Why**: a lower causer may not override a higher one's decision. The solver must not undo what the user selected;
  an application can mark things "on behalf of the user" (APPL_HIGH) or as mere suggestions (APPL_LOW) that the next
  solver run may recompute.
* **Gotcha**: on each solver run every `SOLVER`/`APPL_LOW` transaction is **reset**; only `APPL_HIGH`/`USER` ones
  become solver jobs.
* **See**: [03 §7.3](03-sat-pool-and-resolvables.md#73-resstatus-bit-layout),
  [04 §3.2](04-solver.md#32-from-poolitem-status-to-jobs-satcollecttransact).

### Locks: hard locks, soft locks, taboo

* **Hard lock** (`zypper al`): stored in `/etc/zypp/locks` as `PoolQuery`s, `LOCKED` status, "keep exactly as is".
  **Taboo/Protected** is the UI name for a hard lock. **Soft lock**: not stored; "keep this name not installed".
* **Gotcha**: unlocking an item locked by a *complex* query cannot remove that query – the lock "reappears".
* **See**: [03 §10](03-sat-pool-and-resolvables.md#hard-locks-etczypplocks), [04 §11](04-solver.md#11-locks-and-the-solver).

### License confirmed

* `ResStatus::isLicenceConfirmed()` – a per-item, **non-persistent** bit; zypper `--auto-agree-with-licenses` sets it.
* **See**: [03 §7.3](03-sat-pool-and-resolvables.md#73-resstatus-bit-layout).

### Establish status (satisfied / broken / needed)

* The status of pseudo-installed items (patches) is computed by the solver's establish pass whenever the pool content
  changes, and again after every solver run. See [patch](#patch),
  [04 §8](04-solver.md#8-patches-patterns-and-the-satisfiedbrokenneeded-status).

### Selectable status (`ui::Status`)

* The per-name summary state used by UIs (`S_Install`, `S_AutoDel`, `S_Taboo`, `S_KeepInstalled`, …);
  `Selectable::setStatus(status, causer)` translates it into `ResStatus` changes.
* **See**: [03c §4.5–4.6](03c-respool-and-selectables.md#45-uistatus-the-summary-state).

### Candidates

* **What**: the available item a `Selectable` would install (`candidateObj()`), by default the best one by repo
  priority, arch, edition – with an **equivalent vendor** if something is installed.
* **Gotcha**: candidate choice depends on the solver's `allowVendorChange` flag.
* **See**: [03c §4.4](03c-respool-and-selectables.md#44-the-interesting-objects), [03 §12](03-sat-pool-and-resolvables.md#12-uiselectable-and-respoolproxy-how-yast-sees-the-pool).

## A.8 Solver concepts

### Jobs and requests

* **What**: libsolv solves a list of *jobs* (`SOLVER_INSTALL|SOLVER_SOLVABLE id`, `SOLVER_ERASE|SOLVER_SOLVABLE_NAME
  name`, …) under the dependency rules.
* **In libzypp**: requests are `ResStatus` changes, `Resolver::addRequire/addConflict`, mode flags, or
  `SolverQueueItem`s; `SATResolver::solverInit()` builds the job queue.
* **Gotcha**: problem solutions refer to job indexes, so the order matters.
* **See**: [04 §3.1](04-solver.md#31-job-queue-construction-satresolversolverinit-and-helpers).

### Solve modes: solve, update, dist-upgrade, verify, patch

> How the zypper commands differ in practice (retracted packages, PTFs, blocked updates, exit codes): [18](18-patch-update-dup.md).

* `resolvePool()` (solve requests), `doUpdate()` (plain `zypper up`), `doUpgrade()` (dist-upgrade), upgrade repos
  (`dup --from`), `verifySystem()`, and patching (solve with patches selected).
* **Gotcha**: update, upgrade and verify modes are **sticky** flags until reset.
* **See**: [04 §5](04-solver.md#5-modes).

### Focus

* `ResolverFocus` (`solver.focus`, zypper `--focus`): `Job` (default), `Installed`, `Update`. See
  [04 §15.4](04-solver.md#154-resolverfocus-semantics).

### Problems and solutions

* **What**: when the jobs can't be satisfied, libsolv returns *problems*, each with alternative *solutions* (sets of
  actions: "do not install X", "deinstallation of Y", "remove lock …", "break X by ignoring some of its dependencies").
* **In libzypp**: `ResolverProblem`, `ProblemSolution`; applied via `Resolver::applySolutions()`.
* **Gotcha**: a "remove lock" solution really changes the USER lock and can be persisted.
* **See**: [04 §6](04-solver.md#6-problems-and-solutions), [04 §16](04-solver.md#16-problems-and-solutions-in-depth).

### Vendor stickiness and vendor equivalence

* **What**: by default the solver will not replace an installed package with one from a different (non-equivalent)
  vendor. Vendors are grouped as equivalent in `/etc/zypp/vendors.d/*`.
* **In libzypp**: `VendorAttr::equivalent()`; switches `solver.allowVendorChange` and `solver.dupAllowVendorChange`
  (both default false).
* **Gotcha**: also affects candidate selection and patch relevance.
* **See**: [03 §10](03-sat-pool-and-resolvables.md#vendorattr), [04 §4.2](04-solver.md#42-flag-table).

### Multiversion (kernels)

* **What**: packages that may be installed in several versions at once (kernels, KMPs). Installing a new one does not
  remove the old one.
* **In libzypp**: zypp.conf `multiversion`; old kernels are removed by `PurgeKernels`.
* **Gotcha**: `Package::changelog()` looks up by name only – for kernels you get *some* installed version's changelog.
* **See**: [03 §10](03-sat-pool-and-resolvables.md#multiversion), [04 §13](04-solver.md#13-purgekernels-zyppzypppurgekernelshcc).

### Autoinstalled, unneeded, orphaned, dropped

* **autoinstalled**: installed as a dependency, not requested. **unneeded**: autoinstalled and no longer needed.
  **orphaned**: installed, no repo offers it. **dropped**: in a product's droplist; DUP removes it if it is also
  orphaned (no repo offers it any more).
* **Gotcha**: 3rd-party rpms without a repo count as orphaned (put them in a plaindir repo to protect them).
* **See**: [04 §3.4](04-solver.md#34-gettransaction-and-autoinstalled-tracking), [04 §4.2](04-solver.md#42-flag-table).

### cleandeps

* `SOLVER_CLEANDEPS` on erase jobs also removes the packages that were only installed for the removed one
  (`solver.cleandepsOnRemove`). See [04 §4.2](04-solver.md#42-flag-table).

### Recommends, supplements and onlyRequires

* By default libsolv installs recommends of **newly installed** packages and packages whose supplements become true.
  `onlyRequires` (`--no-recommends`) ignores weak deps **except namespace ones** (language, modalias, filesystem).
* **Gotcha**: the `Resolver.h` doc comment of `setOnlyRequires()` is misleading on this point.
* **See**: [04 §4.3](04-solver.md#43-semantics-that-surprise-people), [04 §18.1](04-solver.md#181-how-the-flags-combine).

### Requested locales and locale packages

* **What**: the languages the user wants (`/var/lib/zypp/RequestedLocales`). Translation packages supplement
  `namespace:language(xx)`.
* **Gotcha**: an empty set is deliberately different from `{en}`. `ZConfig::textLocale()` is a different thing.
* **See**: [03 §9](03-sat-pool-and-resolvables.md#requested-locales).

### PTF (Program Temporary Fix)

* **What**: a SUSE support hotfix: a **PTF master package** (provides `ptf()`) that requires specific
  **PTF packages** (provide `ptf-package()`), replacing official versions until the fix is released.
* **Gotcha**: PTF masters are blacklisted – never picked unless requested.
* **See**: [03a §B.3](03a-special-solvables.md#b3-ptfs-program-temporary-fixes).

### Retracted and blacklisted

* **Retracted**: a package/patch withdrawn by the vendor after release. **Blacklisted** = PTF or retracted: never
  chosen automatically, but installable on explicit request.
* **See**: [03a §B.2](03a-special-solvables.md#b2-retracted-packages-and-patches),
  [03a §B.4](03a-special-solvables.md#b4-blacklisting-in-general).

### SystemCheck

* Extra requirements that must always hold (`/etc/zypp/systemCheck`, `systemCheck.d/*.check`); violations read
  "This request will break your system!". See [04 §10](04-solver.md#10-systemcheck).

### Solver testcase

* **What**: a directory with the complete solver input (repos, `testcase.t`, `zypp-control.yaml`, locks, flags) that
  reproduces a solver run elsewhere.
* **Example**: `zypper --debug-solver` writes one; `zypp-solver-testcase-runner` replays it.
* **Gotcha**: some inputs are not recorded (e.g. `removeOrphaned`, weak items).
* **See**: format and writer [04 §17](04-solver.md#17-test-case-format-in-depth), obtaining and replaying
  [11 §15](11-testing.md#15-bug-reproduction-workflow).

## A.9 Target and commit

### Target, root, installroot

* **Target**: the system being managed – its rpmdb, `@System` solv, `/etc/products.d`, `/var/lib/zypp` state.
  Created by `ZYpp::initializeTarget(root)`.
* **root** (zypper `--root`): the directory the target lives under; repos and caches come from inside it.
  **installroot** (`--installroot`): like `--root` but **shares the host's repositories**.
* **Gotcha**: libzypp does not move the global zypp lock into the root; only `ZYPP_LOCKFILE_ROOT` does.
* **See**: [08 §2–3](08-target-commit-and-rpm.md#3-target-initialisation-rpmdb-and-the-system-cache),
  [08 §11](08-target-commit-and-rpm.md#11-misc).

### rpmdb

* rpm's database of installed packages. Source of truth for "what is installed" and for **trusted GPG keys**
  (`gpg-pubkey-*` pseudo packages). See [08 §3](08-target-commit-and-rpm.md#3-target-initialisation-rpmdb-and-the-system-cache).

### Commit

* **What**: carrying out the solver result: download, verify, install/remove with rpm, run scripts, update state files.
* **In libzypp**: `ZYpp::commit(ZYppCommitPolicy)` → `TargetImpl::commit` → `ZYppCommitResult`. The step list is a
  `sat::Transaction` built from the pool's `ResStatus`.
* **See**: [03 §18](03-sat-pool-and-resolvables.md#18-sattransaction-and-how-commit-uses-it),
  [08 §6](08-target-commit-and-rpm.md#6-the-commit-pipeline-in-detail-targetimplcommitrespool-policy).

### Classic vs single transaction (zypp-rpm)

* **classic_rpmtrans**: one `rpm -U/-e` per package. **single_rpmtrans**: the `zypp-rpm` helper runs **one** librpm
  transaction; needs all packages downloaded first.
* **See**: [08 §5](08-target-commit-and-rpm.md#5-backend-selection-classic_rpmtrans-vs-single_rpmtrans).

### Download modes

`DownloadMode` (`commit.downloadMode`, zypper `--download-*`): download only, in advance, in heaps, or as needed.
See [08 §4](08-target-commit-and-rpm.md#4-zyppcommitpolicy), [08 §15](08-target-commit-and-rpm.md#15-package-provisioning-during-commit-in-depth).

### Delta rpm

* **What**: a `.drpm` holding only the differences between an installed version and the new rpm; the full rpm is
  rebuilt locally with `applydeltarpm`.
* **Gotcha**: off upstream by default (`download.use_deltarpm`); failure falls back to the full rpm.
* **See**: [05 §10.4](05-repositories-and-services.md#104-delta-rpms).

### Package cache

* Downloaded rpms land in `/var/cache/zypp/packages/<alias>/`; kept if `keeppackages`. See
  [05 §10.7](05-repositories-and-services.md#107-package-cache-layout-and-reuse).

### `%posttrans`, needreboot, update messages/scripts

* **`%posttrans`**: rpm scriptlets run at the end of a transaction (emulated by libzypp in classic mode).
  **needreboot**: some packages trigger `/run/reboot-needed`. **Update scripts/messages**: files shipped in
  `/var/adm/update-{scripts,messages}/`.
* **See**: [08 §6](08-target-commit-and-rpm.md#6-the-commit-pipeline-in-detail-targetimplcommitrespool-policy),
  [08 §7](08-target-commit-and-rpm.md#7-needreboot-update-scripts-and-update-messages).

### History log

* `/var/log/zypp/history`: `|`-separated machine-readable lines (`install`, `remove `, `radd   `, `patch  `, …).
* **Gotcha**: the format is parsed by others and by libzypp itself. Never change field positions or padded tokens.
* **See**: [08 §8](08-target-commit-and-rpm.md#8-historylog-varlogzypphistory).

### zypp lock

* **What**: the global "one package manager at a time" lock (`/run/zypp.pid`), taken by `getZYpp()`.
* **Gotcha**: non-root processes never lock.
* **See**: [08 §2](08-target-commit-and-rpm.md#2-zypp-singleton-and-the-global-lock).

### Plugins

Executables under `/usr/lib/zypp/plugins/<type>/` (commit, system, services, urlresolver, repoverification,
sigcheck, appdata) talking a STOMP-like frame protocol. See [08 §9](08-target-commit-and-rpm.md#9-plugins),
[06 §11](06-security-gpg-keyring.md#11-metadata-verification-plugins).

## A.10 Trust

### General vs trusted keyring, gpg-pubkey in the rpmdb

* **What**: libzypp keeps two temporary gpg keyrings: **general** (keys it has *seen*: downloaded `repomd.xml.key`,
  `gpgkey=` URLs, keyhints, the pubkey cache) and **trusted** (keys the admin trusts). Only a signature by a trusted
  key counts as *validated*.
* **Why**: downloading a key from the same server as the data proves nothing. Trust must come from the admin (or from
  an already trusted key, see buddy keys).
* **In libzypp**: `KeyRing`, `PublicKey`. There is **no persistent zypp keyring**: the trusted ring is synced with the
  **rpmdb** (`gpg-pubkey-*` pseudo packages).
* **See**: [06 §2](06-security-gpg-keyring.md#2-concepts), [06 §6](06-security-gpg-keyring.md#6-rpm-database--trusted-keyring).

### Key context

* `KeyContext` – the `RepoInfo` a key/signature belongs to, passed to `KeyRingReport` callbacks so the UI can say
  *which* repo asks.

### gpgcheck, repo_gpgcheck, pkg_gpgcheck, validRepoSignature

* **What**: three tri-state switches: `gpgcheck` (master), `repo_gpgcheck` (master index signature), `pkg_gpgcheck`
  (rpm signatures).
* **Why/Gotcha**: a **validated repo signature** secures the packages through the signed checksums, so rpm signatures
  are only *enforced* when the repo signature is **not** valid.
* **See**: [06 §7](06-security-gpg-keyring.md#7-gpgcheck-semantics-repoinfo--zconfig).

### Accepted vs validated

* `fileValidated()` = the signature was actually verified; `fileAccepted()` = the file may be used (possibly because
  the user or a default said so).
* **Gotcha**: only `fileValidated` makes a repo signature valid; an accepted-but-unvalidated repo still requires
  package signatures.
* **See**: [06 §5.2](06-security-gpg-keyring.md#52-verifyfilecontext).

### Keyhints

* `gpg-pubkey-<id>-<rel>.asc[?fpr=…]` keywords in `repomd.xml` (`RepomdFileReader::keyhints()`), see
  [buddy keys](#b-buddy-keys-gpg-keys-from-repo-keyhints).

### Checksums

* `CheckSum` (md5 … sha512). Every metadata file and rpm is checked against the checksum from the signed metadata;
  problems go to `DigestReport`. See [06 §8](06-security-gpg-keyring.md#8-checksums-and-digestreport).

### Credentials

* User/password for repos: `?credentials=<name>` → `/etc/zypp/credentials.d/<name>`, managed by
  `media::CredentialManager`.
* **Gotcha**: passwords in URLs must be written to `.repo` files but hidden in logs.
* **See**: [06 §9.2](06-security-gpg-keyring.md#92-credentials-zypp-logiczypp-mediaauthcredentialmanagercc),
  [07 §7.16](07-media-and-downloads.md#716-http-authentication-end-to-end).

## A.11 Media

### Url schemes

* `Url` (`zypp-logic/zypp-core/Url.{h,cc}`); schemes `http(s)`, `ftp`, `cd`/`dvd`, `nfs`, `iso`, `file`/`dir`, `hd`,
  `smb`/`cifs`, `plugin`, each served by a media handler.
* **Gotcha**: "downloading" schemes (`Url::schemeIsDownloading()`) behave differently from local ones for refresh and
  delta rpms.
* **See**: [07 §7.6–7.7](07-media-and-downloads.md#76-the-concrete-non-network-handlers-short-reference),
  [02 §8](02-core-infrastructure.md#8-url-zypp-logiczypp-coreurlhcc-urlurlbasehcc-urlurlutilshcc).

### MediaManager, handler, attach point

* **MediaManager**: process-wide registry (`open` → `MediaAccessId`, `attach`, `provideFile`, `release`).
  **MediaHandler**: one per opened medium. **Attach point**: local directory where the medium's content is visible.
* **Gotcha**: network `releasePath` deletes downloaded copies – callers must move or copy files away.
* **See**: [07 §7.3–7.4](07-media-and-downloads.md#74-mediahandler-attach-points-and-the-providerelease-contract).

### Media sets and media number

* **What**: multi-CD/DVD products; each medium has a number. `MediaSetAccess` maps numbers to media and asks the user
  to change discs via `MediaChangeReport`.
* **Gotcha**: without a connected `MediaChangeReport` receiver, errors are simply rethrown.
* **See**: [07 §7.10](07-media-and-downloads.md#710-mediasetaccess-multi-medium-sets-and-media-change).

### Mirrors vs authorities (MirroredOrigin)

* `MirroredOrigin` = one or more **authorities** (the configured baseurls) plus mirrors. Mirrors serve normal files;
  security-relevant files come only from authorities.
* **See**: [07 §7.5](07-media-and-downloads.md#75-mirrors-in-the-media-layer-mirroredorigin).

### Proxies

* From `/etc/sysconfig/proxy` (or libproxy), or per URL with `proxy=`. See
  [07 §7.8](07-media-and-downloads.md#78-url-query-options-and-curlproxy-helpers-zypp-logiczypp-curl),
  [07 §7.17](07-media-and-downloads.md#717-proxy-variants-and-curlconfig-details-to-78).

### Workers (NG)

* In the NG tree, media access runs in separate **worker processes** (`zypp-media-http`, …) driven by the async
  `zyppng::Provide`.
* **Gotcha**: **legacy libzypp never spawns workers** – it uses `MediaManager` in-process; the legacy
  `zyppng::Provide` is only a sync facade.
* **See**: [07 §7.12](07-media-and-downloads.md#712-ng-provide-framework-and-media-workers-ng-only),
  [10 §8](10-zyppng-next-generation.md#8-async-provide-and-the-media-workers-experimental).

## A.12 Application integration

### Reports, callbacks, receivers

* **What**: libzypp's way to report progress and ask questions ("trust this key?", "insert disc 2", "retry
  download?"). Each report type has **one global receiver**.
* **In libzypp**: `callback::SendReport<T>` (library side), `callback::ReceiveReport<T>` (application side); report
  types in `zypp/zypp/ZYppCallbacks.h`.
* **Example**: zypper's receivers live in `zypper/src/callbacks/*.h`.
* **Gotcha**: **without a receiver every question gets its default answer** (often "abort" or "don't trust").
* **See**: [02 §11](02-core-infrastructure.md#11-callback--report-system-zyppzyppcallbackh), [14 §2.6](14-consumers-and-api-surface.md).

### UserData

* `callback::UserData` – a typed key/value bag passed with reports. Also `ZConfig::userData()` (zypper `--userdata`) –
  a string written to the history log. Different things with the same name.

### ZConfig

* `ZConfig::instance()` – singleton holding `zypp.conf` settings, system arch, paths, solver defaults.
* **Gotcha**: zypp.conf of `/` is parsed even for `--root`.
* **See**: [09 §3](09-configuration-and-environment.md#3-zconfig-legacy-architecture),
  [09 §4](09-configuration-and-environment.md#4-zconfig-and-root-changes).

### ZYpp singleton and getZYpp

* `zypp::getZYpp()` returns the `ZYpp::Ptr` that gives access to `pool()`, `resolver()`, `target()`, `keyRing()`,
  `commit()`. Acquiring it takes the zypp lock. See [08 §2](08-target-commit-and-rpm.md#2-zypp-singleton-and-the-global-lock).

### Logging

* Macros `DBG`, `MIL`, `WAR`, `ERR`, …; the application chooses the log file (zypper: `/var/log/zypper.log`).
  `ZYPP_FULLLOG=1` logs everything.
* **See**: [02 §3](02-core-infrastructure.md#3-logging).

### Exceptions

* `zypp::Exception`, always thrown with `ZYPP_THROW` and logged with `ZYPP_CAUGHT`/`ZYPP_RETHROW`.
* **Gotcha**: NG code must use `expected<T,E>` for data-dependent errors, not new exception paths ([zyppng/CONTRIBUTING.md](../zyppng/CONTRIBUTING.md#further-rules)).
* **See**: [02 §4](02-core-infrastructure.md#4-exceptions-zypp-logiczypp-corebaseexceptionhcc).

## A.13 Codebase concepts

### The three tiers

`zypp/` (legacy, production, ABI-stable) → `zypp-logic/` (shared code) ← `zyppng/` (C++20 module, NG rewrite,
paused); never `zypp ↔ zyppng`. Rules: [CONTRIBUTING.md](../CONTRIBUTING.md#where-code-lives),
[zyppng/CONTRIBUTING.md](../zyppng/CONTRIBUTING.md#design-three-tiers). See [00](00-big-picture.md),
[10 §1](10-zyppng-next-generation.md#1-why-ng-exists-and-the-tiers).

### LEGACY-REQUIRED

* A `// LEGACY-REQUIRED` comment at the top of a header in `zypp-logic/*/ng/` marks a class that legacy still needs;
  it must stay until that dependency is gone. See [10 §11](10-zyppng-next-generation.md#11-migration-rules-and-status).

### `LEGACY(n)` macros

* Compile-time guard for deprecated API that disappears at the next soname bump; always 0 in NG builds.
  See [12 §6](12-release-packaging-and-compat.md#6-legacy-guards).

### ZYPP_API and libzypp.map

* Two export filters (`ZYPP_API` + `-fvisibility=hidden`, and the `zypp::*`-only version script); tests link
  `zypp-allsym`, so passing tests don't prove export. See [12 §5](12-release-packaging-and-compat.md#5-symbol-visibility-and-export-control).

### PIMPL, RW_pointer, RWCOW_pointer

* Most public classes keep data in a private `Impl` behind `RW_pointer` or `RWCOW_pointer` (copy-on-write) so the ABI
  stays stable when members change.
* **Gotcha**: non-const access to an `RWCOW_pointer` clones when shared, even for reads.
* **See**: [02 §5](02-core-infrastructure.md#5-smart-pointers-reference-counting-pimpl).

### Sync/async from the same source (MaybeAwaitable)

* Workflow code in `zypp/zypp/ng/` is written once against `MaybeAwaitable<T>`; in legacy it runs synchronously, in
  NG as C++20 coroutines.
* **Gotcha**: `LogicBase`/`AsyncOp` in `logichelpers.h` are dead remnants – don't model new code on them.
