# 03c – ResPool, PoolItem and Selectable: Working with the Pool

This chapter explains, from an API user's point of view, how to **work with** the package pool: how to find things,
how to ask "what is installed, what could be installed", how to request a change, and how to read back what the solver
decided. It covers the three object layers (`sat::Solvable`, `PoolItem`/`ResStatus`, `ui::Selectable`), shows real
excerpts from zypper, and lists the traps that cause "my selection silently did nothing" bugs. Low-level details (bit
layouts, sort orders, store rebuilding) are in [03 §7](03-sat-pool-and-resolvables.md) and
[03 §12](03-sat-pool-and-resolvables.md); this chapter links there instead of repeating them.

> **How the facts were checked.** Every libzypp API name below was checked against the headers
> `zypp/zypp/ResPool.h`, `zypp/zypp/PoolItem.h`, `zypp/zypp/ResStatus.h`, `zypp/zypp/ResPoolProxy.h`,
> `zypp/zypp/ui/Selectable.h`, `zypp/zypp/ui/Status.h`, `zypp/zypp/ui/SelectableTraits.h` and
> `zypp/zypp/sat/SolvableType.h`. Behaviour was read from `zypp/zypp/ui/SelectableImpl.{h,cc}`,
> `zypp/zypp/ui/Selectable.cc`, `zypp/zypp/PoolItem.cc`, `zypp/zypp/pool/PoolImpl.h` and `zypp/zypp/ResPoolProxy.cc`.
> zypper excerpts are quoted from the zypper tree (paths relative to `zypper/`) with line numbers as of October 2026.
> Snippets marked *illustrative* were written for this chapter and were **not compiled**. Nothing here was
> verified by running code.

## 1. The three layers and who uses which

### 1.1 The picture

```
                    ┌──────────────────────────────────────────────────────────────┐
  UI layer          │ ResPoolProxy  (ResPool::instance().proxy())                  │
  "one row per      │   multimap<ResKind, ui::Selectable::Ptr>                     │
   name"            │   ui::Selectable  [kind,name]                                │
                    │     installed(): {PoolItem…}  available(): {PoolItem…}       │
                    │     candidateObj(), status() -> ui::Status (S_Install…)      │
                    └───────────────▲──────────────────────────────────────────────┘
                                    │ groups PoolItems by ident (kind+name)
                    ┌───────────────┴──────────────────────────────────────────────┐
  Transaction       │ ResPool  (ResPool::instance() == getZYpp()->pool())          │
  layer             │   PoolItem = sat::Solvable + ResStatus (+ ResObject, buddy)  │
  "what will        │   ResStatus: installed?, TRANSACT/LOCKED/KEEP, causer, …     │
   happen"          └───────────────▲──────────────────────────────────────────────┘
                                    │ one PoolItem per solvable id (O(1) lookup)
                    ┌───────────────┴──────────────────────────────────────────────┐
  Data layer        │ sat::Pool / sat::Solvable / Repository                       │
  "what exists"     │   libsolv data: name, edition, arch, deps, repo, …           │
                    └──────────────────────────────────────────────────────────────┘
```

* **`sat::Solvable`** is just an id into libsolv. It knows *data* (name, edition, dependencies, repository) and has no
  state. Cheap, copyable, safe to hold. See [03 §6](03-sat-pool-and-resolvables.md).
* **`PoolItem`** is "a solvable plus its `ResStatus`". The `ResStatus` is the **only** place where the
  "install / remove / keep / lock" decision lives. Everything that changes the transaction ends up writing a
  `ResStatus`. See [03 §7](03-sat-pool-and-resolvables.md).
* **`ui::Selectable`** owns **no transaction state of its own**. It is a view that groups all `PoolItem`s with the
  same kind and name: the installed ones and the available ones from every repo. It computes a summary status
  (`ui::Status`) from their `ResStatus`es and translates high-level requests ("install this", "delete this") back into
  `ResStatus` changes on the right items. The only extra state it keeps is a user-chosen candidate (`setCandidate`).

`PoolItem` also derives from `sat::SolvableType<PoolItem>` (`zypp/zypp/sat/SolvableType.h`), so all the
`sat::Solvable` data accessors (`name()`, `edition()`, `arch()`, `repoInfo()`, `isSystem()`, `isBlacklisted()`,
`isRetracted()`, `isPtf()`, `identIsAutoInstalled()`, `multiversionInstall()`, `identical()` …) work directly on a
`PoolItem`. `operator->` gives the `ResObject` for kind-specific data.

### 1.2 Who works on which layer

| Consumer | Layer it mostly uses | Why |
|---|---|---|
| Solver (`zypp/zypp/solver/detail/`) | `PoolItem` / `ResStatus` | reads requests from `ResStatus`, writes results back as `SOLVER` transactions ([04 §3.2](04-solver.md)) |
| Commit (`TargetImpl`, `sat::Transaction`) | `PoolItem` / `sat::Solvable` | what to install/remove is "everything that `transacts()`" |
| zypper | `PoolQuery` → `PoolItem` for decisions, `ui::Selectable` for candidates and display | `install`, `remove`, `info`, `search`, `list-updates` (§5) |
| YaST package selector (libyui-*-pkg, yast2-pkg-bindings) | `ResPoolProxy` / `ui::Selectable` / `ui::Status` | one row per package name, status icons ([14 §3](14-consumers-and-api-surface.md)) |
| PackageKit backend | `PoolItem` + `ResStatus` (`setToBeInstalled` …), Selectables for patches | [14 §4](14-consumers-and-api-surface.md) |

### 1.3 Why the Selectable layer exists

A user thinks in **names**: "is `vim` installed? Which version would I get? Install it." The pool has no single
object for that: `vim` may exist as one installed solvable, plus a dozen available ones from several repos, archs and
versions. Somebody has to answer "which of these is the interesting one" (the *candidate*, decided by repo priority,
arch, vendor and edition), and "what does the user's click mean for each of those items" (e.g. installing a new
version also means marking the old one for removal, and un-transacting other candidates). `ui::Selectable` is that
logic, written once in libzypp so that YaST, zypper and others agree on it.

## 2. ResPool

### 2.1 Getting it

```cpp
ResPool pool( ResPool::instance() );      // zypp/zypp/ResPool.h:74
ResPool same( getZYpp()->pool() );        // zypp/zypp/ZYpp.h:71, returns ResPool::instance()
ResPoolProxy proxy( pool.proxy() );       // ResPool.h:77; also getZYpp()->poolProxy() (ZYpp.h:77)
Resolver & resolver( pool.resolver() );   // ResPool.h:80
```

`ResPool` is a cheap **handle** to the process-wide singleton (`RW_pointer` to `pool::PoolImpl`). Copying it is
fine. There is exactly one pool per process (one libsolv `Pool`), see [00a §A.7](00a-concepts-and-glossary.md).

### 2.2 What it contains

Every solvable of every repository currently loaded into the `sat::Pool`: the `@System` repo (filled from the rpm
database by `Target::load()`, see [03 §5.3](03-sat-pool-and-resolvables.md)) and every repo loaded with
`RepoManager::loadFromCache()` or similar. All kinds are mixed: packages, srcpackages, patches, patterns, products,
applications. Repos that are known to `RepoManager` but not loaded are **not** in the pool.

Items in `@System` have `status().isInstalled()`. This includes installed **patterns** (libsolv's autopatterns for
installed pattern packages) and installed **products** (read from `/etc/products.d`). The only pseudo-installed kind
is the **patch** (`traits::isPseudoInstalled()`, `zypp-logic/zypp/ResTraits.h`): patches are never installed; their
state is the *validate* value (satisfied/broken/not relevant), see §3.4. Products additionally share their status with
the release package (buddy, §3.6).

### 2.3 Iteration and lookup

All iterators deliver `PoolItem`. Most have a `…Begin()/…End()` pair plus an `Iterable` for range-for.

| API (`zypp/zypp/ResPool.h`) | What it does | Cost |
|---|---|---|
| `begin()/end()`, `size()`, `empty()` | all PoolItems | linear |
| `find( sat::Solvable )` (l.111), `find( ResObject::constPtr )` | the PoolItem of a solvable | O(1) |
| `byIdent( kind, name )`, `byIdent( IdString ident )`, `byIdent<TRes>( name )`, `byIdent( PoolItem )`, `byIdent( sat::Solvable )` (l.229–252) | all items of one kind+name (installed and available) | **indexed** (`id2item` multimap) |
| `byKind( ResKind )`, `byKind<TRes>()` (l.276–280) | all items of one kind | filter over all items |
| `byName( std::string )` (l.296) | all items with that name, **any kind** (`resfilter::ByName`) | filter over all items |
| `byStatus( filter::ByStatus )` (l.157) | items whose `ResStatus` predicate is true, e.g. `byStatus( &ResStatus::isToBeInstalled )` | filter over all items |
| `filter( TFilter )` (l.128) | any predicate, e.g. from `zypp/zypp/ResFilters.h` | filter over all items |
| `knownRepositories()`, `knownRepositoriesSize()`, `reposFind( alias )` (l.357–368) | repos that contribute solvables | – |
| `serial()` (l.87) | the pool's `SerialNumber`, changes when the content changes | – |

Prefer `byIdent` when you know the kind and name: it is the only lookup backed by an index. `byName` is a plain
filter and will also hit a pattern or patch named like the package.

Predicates from `zypp/zypp/ResFilters.h` (`resfilter::ByInstalled`, `ByUninstalled`, `ByTransact`, `ByLock`, `ByKeep`,
`ByRecommended`, `BySuggested`, plus `ByName`, `ByRepository`, `ByEdition<>`, `ByArch<>`) and from
`zypp/zypp/Filter.h` (`filter::ByKind`, `filter::ByStatus`) can be passed to `filter()`. See
[03 §15](03-sat-pool-and-resolvables.md) for the full list and caveats.

For anything more complex (substring/regex/glob, dependencies, specific repos), use `PoolQuery`
([03 §13](03-sat-pool-and-resolvables.md)). Its results iterate as `sat::Solvable` (convert with `PoolItem(s)`),
or via `q.poolItemBegin()`/`q.selectableBegin()` as zypper does (§5).

### 2.4 Hard locks, locales and established states

* **Hard lock queries** (l.439–459): `hardLockQueries()`, `hardLockQueriesSize()`, `setHardLockQueries( HardLockQueries )`
  (re-applies locks to all items; usually done when `/etc/zypp/locks` is read on target load) and
  `getHardLockQueries( HardLockQueries & )` (builds queries from the current lock state; used on commit). A hard lock
  shows up on the PoolItem as `status().isLocked()` with causer `USER`. See [03 §10](03-sat-pool-and-resolvables.md).
* **Requested locales**: `setRequestedLocales`, `addRequestedLocale`, `eraseRequestedLocale`, `isRequestedLocale`,
  `isAvailableLocale` (l.401–428), forwarded to `sat::Pool`.
* **Established states**: `changedPseudoInstalled()` (l.350) returns **patches** whose validate state differs from
  the state computed when the pool content last changed, e.g. a patch that becomes `SATISFIED` after the current
  transaction. Commit uses it for history entries.

### 2.5 Serial numbers and staleness (summary)

`ResPool::serial()` is the `sat::Pool` serial. It changes when a repo is created or erased, when solv data are added to
a repo, or when repo info (e.g. priority) is changed (`setDirty()` calls in `zypp/zypp/sat/detail/PoolImpl.cc`).
On the next access `pool::PoolImpl::checkSerial()` notices and invalidates the derived data: the `id2item` index,
the **`ResPoolProxy` (and with it every `ui::Selectable`)** and the established states
(`zypp/zypp/pool/PoolImpl.h:456–470`). Existing `PoolItem`s for solvables that still exist are kept; new ones are
created for new solvables; all are recreated if `sat::Pool::serialIDs()` changed (ids reused). Details in
[03 §5.2, §7.1](03-sat-pool-and-resolvables.md); consequences for applications in §6.

## 3. PoolItem

### 3.1 What it is

```cpp
class PoolItem : public sat::SolvableType<PoolItem>        // zypp/zypp/PoolItem.h:50
{
  ResStatus & status() const;                 // l.76  mutable, even on a const PoolItem
  ResStatus & statusReset() const;            // l.79
  ResStatus & statusReinit() const;           // l.85
  bool isUndetermined() const; bool isRelevant() const;     // l.94–113
  bool isSatisfied() const;    bool isBroken() const;
  bool isNeeded() const;       bool isUnwanted() const;
  ResPool pool() const;                       // l.118
  sat::Solvable buddy() const;                // l.127
  ResObject::constPtr resolvable() const;     // l.133, also operator-> and implicit conversion
  // + everything from SolvableType: satSolvable(), name(), edition(), arch(), ident(), kind(),
  //   repository(), repoInfo(), isSystem(), isBlacklisted(), isRetracted(), isPtf(), identical(), …
};
```

Internally it is a `shared_ptr<Impl>` with the `ResStatus`, the `ResObject::constPtr` and the buddy id
([03 §7.2](03-sat-pool-and-resolvables.md)). Copies share the same `Impl`, so changing `status()` through any copy
changes "the" item.

### 3.2 Getting one

* `PoolItem( sat::Solvable )` (l.58) looks the item up in the pool (`ResPool::instance().find()`). This is the normal
  way after a `PoolQuery` or `sat::WhatProvides`.
* From iteration over `ResPool` or from a `Selectable` (`installedObj()`, `candidateObj()`, `available()` …).
* A default-constructed `PoolItem` is "null"; test it with `if ( pi )` (bool conversion via `SolvableType`).
* You never create new ones; `PoolItem::makePoolItem` is used only by the store.

### 3.3 Identity and equality

* `operator==( PoolItem, PoolItem )` compares the `ResObject` pointers (`PoolItem.h:175`). Inside one pool
  generation this means "same solvable". Do not compare PoolItems obtained before and after a pool rebuild.
* `identical( a, b )` / `a.identical( b )` (`SolvableType.h:102,233`) compares **content**: same name, edition, arch,
  vendor and buildtime. This is how you ask "is this available package the one that is installed?" Installed and
  available copies of the same rpm are different solvables, so they are never `==`, but they can be `identical`.
* `sameNVRA()` compares only name/version/release/arch.

### 3.4 Reading the status

The most useful `ResStatus` queries (`zypp/zypp/ResStatus.h`):

| Query | Meaning |
|---|---|
| `isInstalled()` / `isUninstalled()` | in `@System` or not. Immutable. |
| `transacts()` | will change on commit (install if uninstalled, remove if installed) |
| `isToBeInstalled()` / `isToBeUninstalled()` | `transacts()` combined with the installed bit |
| `isLocked()`, `isUserLocked()`, `isUserLockQueryMatch()` | hard locked; …locked by `USER`; lock comes from `/etc/zypp/locks` |
| `isKept()`, `isSoftLocked()` | KEEP_STATE; KEEP_STATE set by `APPL_LOW` or `USER` |
| `isByUser()`, `isByApplHigh()`, `isByApplLow()`, `isBySolver()`, `getTransactByValue()` | who caused the current state |
| `onSystem()`, `offSystem()`, `staysInstalled()`, `staysUninstalled()`, `wasInstalled()` | the state after commit |
| `isRecommended()`, `isSuggested()`, `isOrphaned()`, `isUnneeded()` | weak information the solver sets |
| `validate()`, `isSatisfied()`, `isBroken()`, `isNonRelevant()`, `isUndetermined()` | establish state of pseudo-installed items |
| `isLicenceConfirmed()` | per-item license bit (not persistent) |

The `PoolItem` shortcuts for patches and patterns (`PoolItem.cc:81–108`):

* `isRelevant()` = not `NONRELEVANT`. `isSatisfied()`, `isBroken()`, `isUndetermined()` forward to the status.
* `isNeeded()` = `isToBeInstalled() || ( isBroken() && !isLocked() )`.
* `isUnwanted()` = `isBroken() && isLocked()` (needed, but the user locked it).

For packages these are meaningless: packages are not established, so they stay `UNDETERMINED`.

### 3.5 Requesting a change

All requests are `ResStatus` calls with a **causer** (`ResStatus::TransactByValue`):

```cpp
pi.status().setToBeInstalled( ResStatus::USER );      // false if pi is installed
pi.status().setToBeUninstalled( ResStatus::USER );    // false if pi is not installed
pi.status().resetTransact( ResStatus::USER );         // back to KEEP_STATE
pi.status().setLock( true, ResStatus::USER );         // lock (USER or APPL_HIGH only)
pi.status().setTransact( yesno, causer );             // the primitive the above use
pi.status().maySetToBeInstalled( causer );            // dry run, no change
```

What the causers mean in practice:

* **`USER`**: an explicit request from the person in front of the screen. The solver turns it into a job and will
  never silently override it; it reports a problem instead.
* **`APPL_HIGH`**: the application requests it on the user's behalf. Also becomes a solver job. Shows up in the history
  log as `pid:exe` instead of `user@host`.
* **`APPL_LOW`** and **`SOLVER`**: proposals. `SATCollectTransact` **resets them at the start of every solver run**
  ([04 §3.2](04-solver.md)), so setting something with `APPL_LOW` and then calling `resolvePool()` effectively
  throws it away (the solver may of course pick the same item again).

Every setter returns `bool`. A lower causer cannot undo a **transaction or lock** set by a higher one; the call just
returns `false`, with no log line and no exception. **Always check the return value.** The "keep" state (no change,
`KEEP_STATE`) is **not** protected: `setTransact()` lets any causer leave it, even if `USER` set it
(`ResStatus.h`, "KEEP_STATE may be changed by any causer"). So a user who *deselected* an item (USER, keep) does not
prevent an application or the solver from selecting it again; use a lock for that. Exact rules (raise-only on repeat,
unlock resets causer to `SOLVER`, …) are in [03 §7.3](03-sat-pool-and-resolvables.md).

> ⚠️ `setTransact( true, USER )` on an item that is LOCKED by `USER` **succeeds** and replaces the lock with
> TRANSACT (`ResStatus.h:438–466`: leaving a non-KEEP state only needs a causer ≥ the current one). A user selection
> therefore silently removes a user lock. zypper works around this (§5.1).

After `resolver.resolvePool()`, items the solver decided to change carry `transacts()` with `isBySolver()`. Your own
requests keep their causer.

### 3.6 The buddy

For products, `buddy()` returns the product's release package; the two share **one** `ResStatus`
(see [00a §A.5](00a-concepts-and-glossary.md#a5-buddy--all-meanings) and [03 §7.2](03-sat-pool-and-resolvables.md#72-poolitem)). Changing or locking
the product changes the release package, and the other way round. `buddy()` returns `sat::Solvable::noSolvable` for
items without a buddy.

## 4. ui::Selectable

### 4.1 Identity: kind + name

A Selectable stands for one **ident**: `ident()`, `kind()`, `name()` (`Selectable.h:115–121`). For packages the ident is
the plain name (`vim`). For other kinds it has a kind prefix (`patch:openSUSE-2026-123`, `pattern:base`,
`product:SLES`). Source packages share the plain ident with packages, but the proxy keys them with a **negated id**
(`zypp/zypp/pool/ByIdent.h:65–86`), so `package:vim` and `srcpackage:vim` are **two different Selectables**.

### 4.2 Getting a Selectable

```cpp
ui::Selectable::Ptr s;
s = ui::Selectable::get( "vim" );                         // package vim         (Selectable.h:93)
s = ui::Selectable::get( ResKind::patch, "SUSE-2026-1" ); // patch               (l.89)
s = ui::Selectable::get( IdString( "pattern:base" ) );    // by ident            (l.85)
s = ui::Selectable::get( pi );                            // the group of a PoolItem (l.105)
s = ui::Selectable::get( solvable );                      // … of a sat::Solvable (l.97)
s = ui::asSelectable()( pi );                             // functor form, used by zypper (l.585)
```

All of them end in `ResPool::instance().proxy().lookup( ident )` (`Selectable.cc:29`). They return a **null `Ptr`** if
nothing with that ident is in the pool, so always check before dereferencing.

To iterate:

```cpp
ResPoolProxy proxy( ResPool::instance().proxy() );
for ( const ui::Selectable::Ptr & sel : proxy.byKind<Package>() ) …   // ResPoolProxy.h:128
for ( const ui::Selectable::Ptr & sel : proxy.byKind( ResKind::patch ) ) …
// also: proxy.begin()/end(), size( kind ), empty( kind ), hasInstalledObj<TRes>()
```

`PoolQuery` can also deliver Selectables (`q.selectableBegin()/selectableEnd()`), used by `zypper info` (§5.4).

### 4.3 The installed set and the available set

* `installed()` (with `installedBegin/End/Size/Empty`): all PoolItems of this ident from `@System`. Usually one; several
  for multiversion packages (kernels). Ordered by `IOrder` (better arch, higher edition, newer install time;
  `SelectableTraits.h:94`).
* `available()`: all PoolItems from repos, ordered **best first** by `AVOrder` (not blacklisted, repo priority, arch,
  edition, buildtime …; [03 §12](03-sat-pool-and-resolvables.md)).
* `picklist()` / `picklistPos( pi )`: available items plus installed items that have no identical available copy.
  This is the list a "choose a version" dialog shows. `picklistPos` returns `ui::Selectable::picklistNoPos` for an
  installed item that has an identical available copy (`Selectable.h:295`).
* Shortcuts: `hasObject()`, `hasInstalledObj()`, `hasCandidateObj()`, `hasBothObjects()`, `hasInstalledObjOnly()`,
  `hasCandidateObjOnly()`, `hasBlacklisted()`, `hasBlacklistedInstalled()`, `hasRetracted()`,
  `hasRetractedInstalled()`, `hasPtf()`, `hasPtfInstalled()`, `isUnmaintained()`, `identIsAutoInstalled()`.

### 4.4 The "interesting" objects

| Method (`Selectable.h`) | Returns | Notes |
|---|---|---|
| `installedObj()` (l.124) | the installed item that transacts, else the first of `installed()` | null if nothing installed |
| `candidateObj()` (l.132) | the available item that transacts, else a user-set candidate (`setCandidate`), else the **default candidate** | the item that *would* be installed. Can be older than the installed one, and can be locked. |
| `updateCandidateObj()` (l.150) | if **nothing is installed**: the default candidate (unless blacklisted). Otherwise the default candidate **only if** it is newer than the installed one, same arch (noarch changes allowed), vendor-equivalent (unless `allowVendorChange`), not blacklisted | null means "no regular update". Non-null does **not** mean an update of an installed package: check `hasInstalledObj()` too, as `zypper list-updates` does. It does **not** check locks. This is the *regular update* rule: it uses `allowVendorChange()`, not the `dupAllow*` flags, and the solver never calls it. Downgrades and arch/vendor changes in `zypper dup` are decided by libsolv ([18 §2](18-patch-update-dup.md#2-what-each-operation-considers)). |
| `highestAvailableVersionObj()` (l.158) | highest edition among available items, ignoring priority and vendor; non-blacklisted preferred | what `zypper lu --all` shows |
| `candidateObjFrom( repo )` (l.140) | best item from one repo, not blacklisted | |
| `theObj()` (l.244) | `candidateObj()`, or `installedObj()` if nothing is available | "pars pro toto": use for summary/description |
| `identicalAvailableObj( pi )`, `identicalInstalledObj( pi )`, `identicalInstalled( pi )`, `identicalAvailable( pi )` | content-identical counterpart | |
| `candidateAsKind<TRes>()` | `asKind<TRes>( candidateObj() )` | |

The default candidate (`SelectableImpl.h:473–506`): if something is installed, the first available item with the
installed arch (or noarch) and an equivalent vendor; if no vendor matches, the first with the same arch; otherwise the
first of `available()`. Because `available()` sorts non-blacklisted first, a **retracted or PTF** item becomes the
candidate only if nothing else qualifies, and `updateCandidateObj()` never returns it.

`setCandidate( pi, causer )` (l.227) chooses another available item as candidate. If the old candidate was already
transacting, the transaction is moved to the new one, provided the causer is allowed to change both; otherwise it
returns a null `PoolItem` and changes nothing (`SelectableImpl.cc:396–434`). `setOnSystem( pi, causer )` (l.237) is the
convenient "make sure exactly this version is on the system": unmodified if an identical item is installed, otherwise
`setCandidate` + `setFate( TO_INSTALL )` (`Selectable.cc:107–112`).

### 4.5 ui::Status: the summary state

`status()` (`Selectable.h:543`) computes a `ui::Status` (`zypp/zypp/ui/Status.h`) from the candidate's and installed
item's `ResStatus` (`SelectableImpl.cc:322–353`), checked in this order:

| Status | When it is reported | In plain words |
|---|---|---|
| `S_Install` | candidate transacts, causer `USER`, nothing installed | "the user wants this installed" |
| `S_Update` | candidate transacts, causer `USER`, something installed | "the user wants this version installed instead" (update, downgrade or reinstall) |
| `S_AutoInstall` / `S_AutoUpdate` | as above, causer not `USER` | "the solver/application will install it" |
| `S_Del` | installed item transacts, causer `USER` | "the user wants it removed" |
| `S_AutoDel` | installed item transacts, causer not `USER` | "the solver/application will remove it" |
| `S_Protected` | installed, and **all** installed items locked | "keep exactly what is installed" |
| `S_Taboo` | not installed, and **all** available items locked | "never install this" |
| `S_KeepInstalled` | installed, no change; also a **satisfied** patch | "stays as it is" |
| `S_NoInst` | not installed, no change | "stays uninstalled" |

`fate()` (`Selectable.cc:252`) reduces this to `TO_INSTALL` (S_Install, S_Update, S_Auto…Install/Update),
`TO_DELETE` (S_Del, S_AutoDel) or `UNMODIFIED`. Shortcuts: `toModify()`, `toInstall()`, `toDelete()`, `unmodified()`,
`locked()` (= S_Protected or S_Taboo), `hasLocks()` (at least one item locked), `onSystem()`, `offSystem()`.
`modifiedBy()` returns the causer of the transacting item, else the candidate's or installed item's causer.

For patches and patterns there are `isRelevant()`, `isSatisfied()`, `isBroken()`, `isUndetermined()` (taken from the
**candidate**), plus `isNeeded()` = `toInstall() || ( !locked() && isBroken() )` and `isUnwanted()` =
`locked() && isBroken()` (`Selectable.cc:222–238`).

### 4.6 Changing state: what each call does to the PoolItems

High-level setters (`Selectable.h:510–549`; all take a causer, default `USER`, and return `bool`):

| Call | Implemented as |
|---|---|
| `setToInstall( c )` | `setFate( TO_INSTALL, c )` → `setStatus( hasInstalledObj() ? S_Update : S_Install, c )` |
| `setToDelete( c )` | `setFate( TO_DELETE, c )` → `setStatus( S_Del, c )` |
| `unset( c )` | `setFate( UNMODIFIED, c )` → `true` if S_Protected/S_Taboo, else `setStatus( S_KeepInstalled or S_NoInst, c )` |
| `setInstalled( c )` | `true` if installed, else `setStatus( S_Install, c )` |
| `setUpToDate( c )` | install if not installed; update if the candidate's edition is higher than the installed one |
| `setDeleted( c )` | `true` if not installed, else `setStatus( S_Del, c )` |
| `setStatus( s, c )` | the translation table below |

`setStatus()` (`SelectableImpl.cc:355–394`, using `StatusHelper` l.150–313). Every step saves the touched
`ResStatus`; if any step fails, **all** changes are rolled back and `false` is returned.

| Target status | Precondition | Effect on PoolItems |
|---|---|---|
| `S_Install` | candidate, nothing installed | unlock + un-transact **all** available items, then `cand.setTransact( true, c )` |
| `S_Update` | candidate and installed | every installed item: un-transact, unlock, and (if the candidate is not multiversion) `setTransact( true, SOLVER )` as a removal *hint*. Then like S_Install for the candidate |
| `S_Del` | installed | un-transact all available items; unlock + transact every installed item |
| `S_KeepInstalled` / `S_NoInst` | installed / not installed | un-transact + unlock every installed and every available item |
| `S_Protected` | causer `USER`, installed | un-transact available items; lock every installed item |
| `S_Taboo` | causer `USER`, candidate | un-transact + lock every available item |
| `S_AutoInstall`, `S_AutoUpdate`, `S_AutoDel` | – | **always `false`**: "Auto level is SOLVER level. UI may query, but not set" |

Two consequences that surprise people:

* **Install/update/keep unlock.** `setStatus( S_Install )` removes locks on all available items, and
  `S_KeepInstalled` removes the lock from installed items. For a UI that is intended ("the user clicked it"). For a
  tool that respects `/etc/zypp/locks`, it means locks disappear silently. They are written back on commit
  ([00a §A.7](00a-concepts-and-glossary.md)).
* **The solver-level removal hint.** After `S_Update` the old version shows as `isToBeUninstalled()` by `SOLVER`
  even before solving. The next solver run resets it and decides again.

### 4.7 Multiversion: per-item picks

For multiversion packages (kernels; `multiversionInstall()`, l.374) the summary status is not enough: you may want to
install two versions and remove a third. Use the per-item API:

* `pickInstall( pi, c, yesno )`, `pickNoInstall( pi, c )`, `pickDelete( pi, c, yesno )`, `pickNoDelete( pi, c )`
  (l.378–391).
* `pickStatus( pi )` (l.417) computes a `ui::Status` for one item and its identical copies; `setPickStatus( pi, s, c )`
  (l.420) sets it.

`setPickStatus` (`SelectableImpl.cc:450–571`) handles multiversion candidates by transacting just that item (and
un-transacting non-multiversion ones). For a **non-multiversion** item it falls back to `setCandidate` +
`setStatus( S_Install/S_Update )`, i.e. picking one version deselects every other. `pickStatus` returns `Status(-1)`
for a PoolItem of another ident.

### 5.1 `zypper install foo` (`zypper/src/SolverRequester.cc`)

`SolverRequester::install( const PackageSpec & )` (l.220–346) first tries the argument as a name:

([03 §15](03-sat-pool-and-resolvables.md)). Then, per best match:

```cpp

ui::Selectable::Ptr s( ui::asSelectable()( *sit ) );

  installPatch( pkg, *sit );
else {

    PoolItem best { s->updateCandidateObj() };

    if ( userconstraints )            updateTo( pkg, *sit );
    else if ( _opts.force )           updateTo( pkg, s->highestAvailableVersionObj() );
    else if ( best )                  updateTo( pkg, best );
    else if ( changes_vendor && !_opts.allow_vendor_change ) updateTo( pkg, instobj );
    else                              updateTo( pkg, *sit );
  }
  else if ( _command == ZypperCommand::INSTALL )
    setToInstall( *sit );
}
```

Points to note:

* `get_installed_obj()` (l.106–120) treats pseudo-installed kinds (patches only) specially: a patch counts as
  "installed" if an available item `isSatisfied()`; for every other kind it is `s->installedObj()`.
* `updateCandidateObj()` is used as "the policy-conforming update", and zypper adds its own lock check because
  `updateCandidateObj()` ignores locks.
* If nothing matches by name, zypper falls back to `sat::WhatProvides` and adds a solver **requirement** instead of
  marking an item (l.321–345).

The actual marking is `setToInstall()` (l.772–800):

```cpp
// SolverRequester.cc:774-798
if ( _opts.force )
  pi.status().setToBeInstalled( ResStatus::USER );
else if ( ui::asSelectable()(pi)->hasLocks() ) {
  // Workaround: Use a solver request instead of selecting the item.
  // This will enable the solver to report the lock conflict, while
  // selecting the item will silently remove the lock.
  sat::Solvable solv( pi.satSolvable() );
  Capability cap( solv.arch(), solv.name(), Rel::EQ, solv.edition(), solv.kind() );
  getZYpp()->resolver()->addRequire( cap );
  …
}
else
  ui::asSelectable()(pi)->setOnSystem( pi, ResStatus::USER );
```

This is the canonical illustration of §3.5/§4.6: selecting a locked item would silently unlock it, so zypper asks the
solver via `addRequire()` and gets a proper "locked" problem instead. Without locks it uses
`Selectable::setOnSystem()`, which sets the candidate and installs it.

## 6. Lifecycle and invalidation

### 6.1 What invalidates what

| Event | `sat::Solvable` | `PoolItem` | `ui::Selectable` / `ResPoolProxy` |
|---|---|---|---|
| Solver run, status changes | valid | valid; status may change | valid |
| Repo added (`loadFromCache`, `addRepository…`) | valid | existing ones kept | **proxy dropped and rebuilt** on next `proxy()` |
| Repo removed (`reposErase`, `removeRepository`) | ids of that repo become invalid | items of that repo dropped from the store | **dropped** |
| Target (re)load (`Target::load()`, after commit with `syncPoolAfterCommit`) | `@System` solvables replaced | new `@System` items | **dropped** |
| All repos removed, ids reused (`serialIDs` change) | all ids may now mean something else | **all recreated** | **dropped** |

A dropped proxy is not destroyed while you hold a `ResPoolProxy` or `Selectable::Ptr`: both are ref-counted and keep
the old `PoolItem`s alive. What happens to status changes through such a stale object depends on the item:
* **Items the pool kept** (`pool::PoolImpl::store()` keeps a `PoolItem` as long as its solvable exists and ids were
  not reused): the old Selectable holds the *same* `PoolItem`, so changes still reach the live `ResStatus`. What the
  stale Selectable lacks is the new state of the pool, e.g. new candidates from an added repo.
* **Items that were dropped or recreated** (their repo was removed, the target was reloaded, or all ids were reused):
  changes modify `ResStatus` objects the pool no longer uses, so **they are silently lost**.

Stale `sat::Solvable` ids return default values (or data of a reused id).

### 6.2 Safe patterns for long-running applications

* **Do not cache** `ResPoolProxy`, `Selectable::Ptr` or `PoolItem` across anything that can change repos or the
  target. Re-fetch them (`ui::Selectable::get( ident )`) after such operations. Cache *idents* (`IdString`) or
  name/kind strings instead. Raw solvable ids are not safe to cache.
* If you must detect change, remember `ResPool::instance().serial()` with a `SerialNumberWatcher`
  (`zypp-logic/zypp/base/SerialNumber.h`) and refresh when it changes.
* Use `ResPoolProxy::saveState()`, `restoreState()`, `diffState()` and `scopedSaveState()`
  (`ResPoolProxy.h:172–207`) to implement "cancel" in a dialog. They save and restore the `ResStatus` of all items
  (via `PoolItem::saveState`). PackageKit's `PoolStatusSaver` does this; it must be created **after** the pool is built,
  otherwise locks are lost (bnc#804054, [14 §4](14-consumers-and-api-surface.md)).
* After commit with `ZYppCommitPolicy::syncPoolAfterCommit(true)` the target is reloaded; treat everything as stale.

### 6.3 Threading

There is no locking anywhere in `ResPool`, `PoolItem`, `ResStatus`, `ResPoolProxy` or `Selectable` (from reading the
code: lazy rebuilds in `pool::PoolImpl` use `mutable` members without synchronisation). Treat the whole pool as
**single-threaded**: all access from one thread, or under one application-level mutex as PackageKit does
([14 §4](14-consumers-and-api-surface.md)). Even "read-only" calls like `proxy()` or `byIdent()` can trigger a rebuild.

## 7. Pitfalls and special cases

* **Silent refusals.** Every setter returns `bool`; a lower causer cannot undo a transaction or lock set by a higher one,
  and nothing is logged. A typical bug: an application sets `APPL_LOW`, the user had selected the item with `USER`
  earlier, and the request just does nothing. A USER "keep" (deselection) is *not* protected: any causer can
  transact the item again.
* **`APPL_LOW`/`SOLVER` requests vanish on solve.** They are reset by `SATCollectTransact` at the start of every run
  ([04 §3.2](04-solver.md)). Use `APPL_HIGH` or `USER` for real requests.
* **Selecting unlocks.** `ResStatus::setTransact( true, USER )` on a USER-locked item replaces the lock;
  `Selectable::setStatus( S_Install/S_Update/S_KeepInstalled/S_Del )` explicitly unlocks. zypper therefore uses
  `addRequire`/`addConflict` for items with `hasLocks()` (§5.1).
* **`S_Auto*` cannot be set.** `setStatus( S_AutoInstall … )` always returns `false`.
* **`S_Protected`/`S_Taboo` can only be set by `USER`**, but `status()` reports them for locks of any causer.
* **`installedAsKind<TRes>()` returns the candidate.** `Selectable.h:205–207` implements it as
  `asKind<TRes>( candidateObj() )`, not `installedObj()`. Use `asKind<TRes>( sel->installedObj() )` instead.
  (Looks like a long-standing bug; changing it is a behaviour change for consumers.)
* **`candidateObj()` is not "the newest" and not "an update".** It may be older than the installed version (repo
  priority, vendor), and it may be locked. Use `updateCandidateObj()` for "regular update" and
  `highestAvailableVersionObj()` for "newest anywhere". None of them check locks.
* **Candidate depends on solver flags.** `defaultCandidate()` and `updateCandidateObj()` consult
  `ResPool::instance().resolver().allowVendorChange()`, so changing that flag changes the candidates.
* **Multiversion.** `status()` looks only at `installedObj()` and `candidateObj()`. With several kernels installed or
  selected, use `pickStatus()`/`pickInstall()`/`pickDelete()` per item. `updateCandidateObj()` is computed only
  against the newest installed instance.
* **srcpackage vs package.** Same ident string, different Selectables (negated id). `Selectable::get( "foo" )` and
  `Selectable::get( IdString( "foo" ) )` give the **package**; use `get( ResKind::srcpackage, "foo" )` for the source
  package. `PoolItemBest` and `ResPool::byName` do **not** separate them ([03 §15](03-sat-pool-and-resolvables.md)).
* **Products share status with the release package** (buddy). Locking or selecting one affects the other; a
  product may appear to "transact" because its release package does.
* **Patches are the only pseudo-installed kind.** A patch is never `isInstalled()`; a satisfied patch reports
  `S_KeepInstalled` and `installedObj()` is null. Use `isSatisfied()`/`isBroken()` or zypper's `get_installed_obj()`
  approach (§5.1). Patterns and products are ordinary installed items in `@System` (`isInstalled()`, `installedObj()`);
  products also share their status with the release package (buddy).
* **Retracted and PTF items** sort last in `available()`, are never returned by `updateCandidateObj()`,
  `candidateObjFrom()` or (if anything else exists) `highestAvailableVersionObj()`. They can still be the
  `candidateObj()` when nothing else is available or when set with `setCandidate()`. See
  [03 §11](03-sat-pool-and-resolvables.md) and [03a](03a-special-solvables.md).
* **Equality vs identity.** `==` means the same solvable; use `identical()` to match an installed item with its
  repo copy.
* **Stale handles** (§6): a Selectable fetched before the pool changed misses new items (e.g. candidates from an added
  repo). Status changes through it are lost without any error for items that were dropped or recreated (repo
  removed, target reloaded, ids reused); for items the pool kept they still take effect. Fetch Selectables again
  after changing the pool.
* **Typedef oddity.** `SelectableTraits::installed_iterator` is declared as `AvailableItemSet::iterator` although the
  container is an `InstalledItemSet` (`SelectableTraits.h:123–126`). It works because both are `std::set<PoolItem>`
  iterators; do not rely on the comparator type.

## 8. Where to start when debugging

* **Stream operators.** `MIL << pi` prints the compact `ResStatus` then the solvable (`PoolItem.cc:154`). The status
  letters (`ResStatus.cc:102–128`): `I`/`U` installed/uninstalled; `B`/`S`/`N`/`_` broken/satisfied/not
  relevant/undetermined; `T`/`L`/`_` transact/locked/keep; causer `s`/`l`/`h`/`u` (solver, appl_low, appl_high,
  user); detail `O`/`U`/`S`; then `r`/`s`/`o`/`u` for recommended/suggested/orphaned/unneeded. Example: `U_Tu_` = not
  installed, to be installed by the user.
* `MIL << *sel` prints `[kind]name: status (I n) (A m)` plus the candidate. `dumpOn( str, *sel )` or `MIL << dump( sel )`
  (`dump()` from `zypp-core/base/LogTools.h`) lists every installed and available item, marking the installed object
  `i`, the candidate `c`/`C` (C = also the update candidate) (`SelectableImpl.h:552`).
* `MIL << proxy` / `dumpOn( str, proxy )` for the whole proxy; `MIL << pool` for the pool.
