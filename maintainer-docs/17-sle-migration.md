# 17 – SLE Migration (`zypper migration` and Friends)

This chapter follows a SUSE Linux Enterprise migration (service pack or major
version) from start to finish. It shows which tool does what, where libzypp
takes part, which libzypp features exist mainly *because* of migrations, and how
to triage a migration bug that landed on libzypp. Most of these bugs get
assigned to libzypp first, even when the cause is elsewhere.

> **How the facts were checked (Nov 2026).**
> * `zypper migration`: read from the public `SUSE/connect-ng` sources
>   (`cmd/zypper-migration/migration.go`, `internal/zypper/`,
>   `internal/connect/migration.go`, `DIFFERENCES.md`).
> * YaST: `yast/yast-migration` on GitHub and the local `yast-pkg-bindings`.
> * libzypp, zypper and libsolv: the local trees and changelogs.
> * Bug examples: bugzilla.suse.com.
>
> Nothing was run against SCC or RMT. Statements about server-side behaviour
> come from client code and bug reports.

## 1. Terminology

| Term | Meaning |
|---|---|
| **Service pack (SP) migration** | Same major version, next SP, e.g. SLES 15 SP6 → SP7 |
| **Major version migration** | e.g. SLES 15 SP7 → SLES 16.0. Brings big transitions: usrmerge, rpmdb location, `/usr/etc` configs, new keys |
| **Online migration** | Done on the running system. The **old** system's zypper, libzypp and libsolv compute and run the upgrade |
| **Offline migration** | Done from installation media or an installer environment ("instsys") on a mounted target root. The **media's** tools do the work |
| **Migration target / path** | The set of products (base + modules/extensions) to upgrade to. Offered by SCC/RMT, not by libzypp |
| **SCC / RMT / SMT** | SUSE Customer Center and the on-premise mirroring/registration proxies. They provide the repos (as services) and the migration paths |
| **`zypper dup`** | The dependency-solving step that actually migrates packages. Without the registration steps it doesn't change repos or products |

| Layer | Role in a migration | Bugs that belong here |
|---|---|---|
| **SCC / RMT** | Which paths are offered, which repos each product has, which modules block a migration | "No migration available", "module X blocks the migration", missing repos on RMT |
| **`zypper migration`** (package `suseconnect-ng`; formerly the Ruby `zypper-migration-plugin`) | Orchestration: self-update, path selection, repo backup/restore, service switching, release-package install, calling `zypper dup` | Wrong order of steps, rollback, flag passthrough, error handling |

| **zypper** | CLI options and exit codes used as the interface | Option handling, output |
| **libzypp** | `$releasever`, services, refresh, keys, DUP job building, commit | Most of the rest of this chapter |
| **libsolv** | The actual solving, product ↔ release-package links | Wrong solver decisions on correct input |
| **rpm, packages** | Scriptlets, file conflicts, usrmerge, rpmdb | Scriptlet failures, conflicting files |

**Bugzilla:** there is a dedicated `Migration` component for SLE products

## 3. `zypper migration` step by step

`zypper migration` is the program `zypper-migration`, found by zypper's
subcommand mechanism. It lives in `SUSE/connect-ng`, `cmd/zypper-migration/`,
and talks to zypper **only through the command line** (`internal/zypper/`).

| # | Step | What runs | libzypp involved |
|---|---|---|---|
| 1 | **Self-update** of the update stack, then restart itself (`--no-selfupdate` skips it) | `zypper patch --updatestack-only`, re-checked with `zypper patch-check` | patches, update stack ([03a §B.1](03a-special-solvables.md#b1-patches-the-metadata)) |
| 2 | Refresh repos. A failure here stops the migration **before** missing release packages (and any keys they ship) are installed | `zypper ref` | refresh ([05 §5](05-repositories-and-services.md#5-refresh-deciding-downloading-caching)) |
| 3 | Check that a release package exists for every registered product; install missing ones (bsc#1171652) | `zypper --no-refresh install --no-recommends --auto-agree-with-product-licenses -t product <id>` | products ([03a §A2](03a-special-solvables.md#a2-products)) |
| 4 | Ask SCC/RMT for paths (`/connect/systems/products/migrations`; offline: `…/offline_migrations`), let the user choose | – | reads installed products via `zypper --xmlout products -i` |
| 5 | Pre snapshot (`snapper create`), then set `DISABLE_SNAPPER_ZYPP_PLUGIN=1` so the commit doesn't make its own snapshots (bsc#947270) | snapper | commit plugins ([08 §9](08-target-commit-and-rpm.md#9-plugins)) |
| 6 | **Back up** `/etc/zypp/repos.d`, `/etc/zypp/credentials.d`, `/etc/zypp/services.d` and `/etc/products.d` into `/var/adm/backup/system-upgrade/repos.tar.gz`, plus a restore script `repos.sh` | – | – |
| 7 | Leap → SLES only: disable all old repos (bsc#1184237) | `zypper modifyrepo -d` | – |
| 8 | Per product: SCC upgrade call, then switch the service (add or remove RIS services, `refs`). Remove SUSE services without a migration (bsc#1161891). Disable obsolete repos | `zypper addservice -t ris`, `removeservice`, `modifyservice`, `refs` | services ([05 §7](05-repositories-and-services.md#7-services)) |
| 9 | Refresh with the **new** `$releasever` | `zypper --releasever <new> ref -f` | repo variables ([05 §6](05-repositories-and-services.md#6-repo-variables-zyppzyppreporepovariableshcc)) |
| 10 | **Distribution upgrade** | `zypper --releasever <new> --no-refresh [-n] dist-upgrade [--auto-agree-with-licenses] --no-allow-vendor-change <passthrough>` | DUP ([04 §5.3](04-solver.md#53-doupgrade-dist-upgrade)) and commit ([08](08-target-commit-and-rpm.md)) |
| 11 | **`dup` exit code 8** (commit error): print "most likely in an inconsistent state", recommend a snapshot rollback or backup restore, and **exit 2 at once**: no post snapshot, no repo restore, no SCC rollback. **Any other failure:** post snapshot, restore the repo backup, run the SCC rollback, exit 1. **Success:** post snapshot, check that all release packages are installed | `repos.sh`, SCC rollback (`internal/connect/migration.go`) | – |

Details worth knowing:

* **`--releasever` is not persistent.** zypper's `--releasever` only sets
  `ZYPP_REPO_RELEASEVER` for that one process (`zypper/src/Config.cc`).
  After the migration, `$releasever` comes from the newly installed base product
  ([08 §13](08-target-commit-and-rpm.md#13-products-on-the-target-etcproductsd-baseproduct-releasever)).
  If the new release package isn't installed or the `baseproduct` symlink is
  wrong, later `zypper ref` runs use the **old** value. The base product's
  `-release` package ships that symlink itself (e.g. `openSUSE-release.spec`:
  `ln -s openSUSE.prod …/products.d/baseproduct`).
* **Vendor change.** `zypper migration` always passes `--no-allow-vendor-change`
  to `zypper dup` unless `--allow-vendor-change` is given, so the `zypp.conf`
  default (`solver.dupAllowVendorChange`) is **ignored** (comment in
  `zypperDupArgs()`).
* **Exit codes.** With `--strict-errors-dist-migration` only "fatal" zypper
  errors fail the migration: any code from 1 to 99, plus 104
  (`INF_CAP_NOT_FOUND`), 105 (signal) and 106 (`INF_REPOS_SKIPPED`). Other codes
  ≥ 100, such as "reboot needed", are ignored. Exit code **8** (commit error)
  marks the file system as possibly inconsistent. In that case `zypper migration`
  exits with 2 **without** undoing anything: the repos stay switched, the SCC
  registration stays at the target, and there is no post snapshot (step 11).
* **Passthrough options to `dup`:** `--debug-solver`, `--recommends`,
  `--no-recommends`, `--replacefiles`, `--details`, `--download`,
  `--download-only`, `--from`, `--repo`, `--auto-agree-with-licenses`, vendor
  change. Run `zypper migration --help` for the current list.
* **Offline mode.** `--product name/version/arch` is only allowed together with
  `--root` (it asks SCC for `offline_migrations`). With `--root`, no snapshots
  are created.
* **Interruptions.** SIGINT/SIGTERM are only honoured between steps. zypper's
  exit code is still checked afterwards.

### 3.1 YaST

`yast2-migration` (`yast/yast-migration`) does the same with a UI:
* Registration and repo switching through `yast2-registration`
  (`registration_sync` on rollback).
* Its own snapper pre/post snapshots.
* It solves inside the YaST process through `yast2-pkg-bindings`:
  `Pkg.PkgUpdateAll` → `Resolver::doUpgrade()`, with the DUP flags passed as
  options (`dupAllowVendorChange`, … in `yast-pkg-bindings/src/Package.cc`),
  then `Pkg.PkgSolve`.

Here libzypp runs **in-process**, so logs go to the y2log, not `zypper.log`
([02 §3](02-core-infrastructure.md#3-logging)).

Agama (the SLE 16 installer) has no upgrade or migration code (checked in its
repository tree).

## 6. Major-version transitions (SLE 15 → 16)

| Transition | Where it hits libzypp | Notes |
|---|---|---|
| **usrmerge** | The `filesystem` package must not be upgraded in a single rpm transaction on a non-merged system. libzypp falls back to the classic backend (bsc#1189788, bsc#1236481); `ZYPP_NO_USRMERGE_PROTECT=1` bypasses this | Since 17.37.14 the classic backend also **unsets** `ZYPP_SINGLE_RPMTRANS` and sets `ZYPP_CLASSIC_RPMTRANS=1` for scriptlets. Before that, scriptlets could believe they ran in a single transaction (bsc#1246038) |
| **rpmdb location** `/var/lib/rpm` → `/usr/lib/sysimage/rpm` | libzypp re-creates the compat symlink at init and after each commit | [08 §3](08-target-commit-and-rpm.md#3-target-initialisation-rpmdb-and-the-system-cache) |
| **Configs moving to `/usr/etc`** | `zypp.conf` merging (UAPI.6), rpmsave handling in the spec | [09 §2](09-configuration-and-environment.md#2-locating-and-merging-zyppconf) |
| **New signing keys and algorithms** (e.g. SHA1 removed for FIPS, bsc#1240529; post-quantum signatures) | Key import during refresh, sigcheck plugins (`repo_sigcheck_plugin=pqcverification`, bsc#1273058) | [06 §11](06-security-gpg-keyring.md#11-metadata-verification-plugins) |
| **Product variants built from the same sources** (e.g. `SLES-release` and `SLES_immutable-release`) | libsolv picks the release package for an auto-product by **build time**. Reproducible builds give both the same build time, so it picked the wrong one and the upgrade wanted both release packages (bsc#1279541) | See §7 |

## 7. A lesson from bsc#1279541: the old system's solver does the work

The bug: migrating SL Micro 6.2 → SLES 16.1 made `zypper dup` want to install
both `SLES-release` and `SLES_immutable-release`, which then conflicted on
`/etc/products.d/SLES.prod`.

* **Cause:** both release packages provide `product(SLES) = 16.1-0`. libsolv
  links an auto-product to its release package and, if several match, filters
  by build time. With reproducible builds the build times were equal (both come
  from `SOURCE_DATE_EPOCH` of a shared changes file).
* **Fix:** libsolv 0.7.40 (commit `fd9918b7`, "linkedpkg: also take
  autoproduct() provides into account").
* **Why it needed a libzypp release:** libzypp links libsolv **statically**
  ([01 §7](01-layout-build-and-dependencies.md#7-libsolv-linking)). So libzypp
  17.38.16 had to `BuildRequire` libsolv ≥ 0.7.40 and be rebuilt.
* **Why it had to ship to the *source* distributions:** in an online migration
  the **old** system's libzypp/libsolv computes the upgrade. The fix therefore
  had to be released for the source products. For offline migrations it has to
  be in the installer environment. The release notes had to say "install this
  update before migrating".

General rules from this:
1. A migration bug in solving is fixed by updating the **source** system's
   stack (online) or the **installer** (offline), not the target.
2. A libsolv fix means rebuilding libzypp.
3. `zypper migration`'s self-update step (§3, step 1) is what brings such fixes
   onto the source system first. That only works if the fix is released as an
   update-stack patch for the source product.

## 8. Failure catalogue

| Symptom | Likely cause | Owner | Ask for / check |
|---|---|---|---|

| Many "deinstallation of X" or "keep obsolete" choices | Vendor change needed (`--allow-vendor-change`), droplists, PTFs, retracted packages | Expected behaviour or product | testcase; vendors of the affected packages |
| Two release packages / file conflicts on `/etc/products.d/*.prod` | Release-package linking (bsc#1279541) | libsolv / libzypp | testcase; libsolv and libzypp versions on the **source** system |
| File conflicts between packages (bsc#1230586) | Packaging | Package maintainers | the conflicting packages' file lists |
| Scriptlet failures around `filesystem` / usrmerge | usrmerge transition, rpm backend | packaging and libzypp | `zypper.log` (backend line), `ZYPP_SINGLE_RPMTRANS` setting |
| Module or extension missing after migration (bsc#1171652) | Release package not installed, SCC out of sync | connect-ng / SCC | `/etc/products.d`, `SUSEConnect --status` |

## 9. Reproducing and debugging

* **Get the solver testcase.** `zypper migration --debug-solver` passes the
  option to `zypper dup` and writes `/var/log/zypper.solverTestCase`. A DUP that
  reaches the commit (not `--dry-run`, and unless
  `solver.upgradeTestcasesToKeep=0`) also leaves
  `/var/log/updateTestcase-<date>` (the one in bsc#1279541 was enough to find
  the cause). If the migration fails while solving, only `--debug-solver`
  gives you a testcase. Replay it as described in
  [11 §15](11-testing.md#15-bug-reproduction-workflow).
* **Logs.**
  * `/var/log/zypper.log` covers all the zypper runs the migration made; each
    one starts with a banner ([02 §3](02-core-infrastructure.md#3-logging)).
  * The migration tool's own output is on the console only.
  * For YaST, use the y2logs.
* **The repo backup** (contains `credentials.d` and repo URLs with tokens: never ask for it to be attached as
  is). `/var/adm/backup/system-upgrade/repos.tar.gz` holds the
  pre-migration repos, services, credentials and products: useful to see the
  starting point.
* **Simulate the solver step without SCC.** Mirror or prepare the target repos
  locally, then run `zypper --releasever <new> dup --dry-run` (add `--root` for
  a copy of the system). This exercises libzypp/libsolv. It does not test the
  SCC service switching.
* **Check the versions on the source system.** Many fixes only help if they are
  installed *before* migrating (§7): `rpm -q libzypp zypper libsolv-tools`.

## 10. Pitfalls & special cases

* **The source system's stack decides.** Fixes for migration solving must be
  shipped to the old product (online) or the installer (offline).
* **libsolv fixes need a libzypp rebuild** (static linking).
* **`--releasever` is a one-shot override** (environment variable). The
  persistent value comes from the base product after the upgrade.
* **`zypper migration` ignores the `zypp.conf` vendor-change default.** It
  always passes `--no-allow-vendor-change` unless asked.
* **No snapshots with `--root`,** and only one pre/post pair otherwise (the
  snapper zypp plugin is disabled by `DISABLE_SNAPPER_ZYPP_PLUGIN=1`).
* **Exit codes ≥ 100 are mostly ignored** by the strict mode, except 104–106.
* **A commit failure (exit 8) is not rolled back by `zypper migration`.** It exits 2
  right away: repos stay switched, SCC still has the target registration, and no
  post snapshot is made. Recovery is a snapshot rollback or a backup.
* **The repo backup covers only `/etc/zypp/{repos,services,credentials}.d`
  and `/etc/products.d`,** not packages. Package rollback needs snapper.
* **Reproducible builds can make build time useless** as a tie-breaker
  (bsc#1279541).
* **Leap → SLES disables all old repos** first (bsc#1184237).
* **Many "migration" bugs aren't libzypp bugs.** Plugin flow, SCC/RMT state and
  packaging conflicts are common; reassign early (bsc#1213506 is an example of
  a plugin bug filed against libzypp).

## 11. Where to start when debugging

1. Which tool ran the migration (zypper migration, YaST, plain `zypper dup`),
   online or offline?
2. The versions of libzypp, zypper and libsolv on the **source** system (or the
   installer).
3. Which step failed (§3)? The console output of `zypper migration` usually
   shows the failing zypper command line.
4. Solving problem: get the testcase (§9). Refresh or key problem: `zypper.log`
   around the `--releasever` refresh. Commit problem: history and the backend
   line in `zypper.log`.
5. Decide the owner with §2 and §8 before reading code.
