# 18 – Updating a System: patch vs update vs dist-upgrade

There are several ways to bring a system up to date: `zypper patch`, `zypper
update`, `zypper dist-upgrade` and plain `zypper install`. They behave
differently in ways that surprise users, and the resulting "why wasn't X
updated?" reports often land on libzypp. This chapter compares the operations
side by side: which libzypp mode each uses, what it considers, and how each one
treats retracted packages, PTFs, locks, vendors and blocked updates.

Concepts are explained in their home sections. This chapter links to them:
patches [03a §B.1](03a-special-solvables.md#b1-patches-the-metadata), retracted
[03a §B.2](03a-special-solvables.md#b2-retracted-packages-and-patches), PTFs
[03a §B.3](03a-special-solvables.md#b3-ptfs-program-temporary-fixes), solver
modes [04 §5](04-solver.md#5-modes).

## 1. The operations at a glance

| Command | What zypper asks libzypp for | libzypp entry point | Problems shown? |
|---|---|---|---|
| `zypper patch` | Install every **needed** patch (two passes: update-stack patches first, the rest only if none were found) | patch items set to install, then `resolvePool()` | yes |
| `zypper patch --with-update` | Same, plus "update everything else that can be updated" | `setUpdateMode(true)` + `resolvePool()` | yes |
| `zypper update` (no arguments) | Update every installed package as far as possible | **`doUpdate()`**, a separate code path | **no**: blocked updates are kept silently |
| `zypper update foo` | Update `foo` | request for a newer `foo`, then `resolvePool()` | yes |
| `zypper update -t patch` | Same as `zypper patch` (without `--with-update`) | as `patch` | yes |
| `zypper dist-upgrade` | Upgrade the whole system to what the repos offer | **`doUpgrade()`** | yes |
| `zypper dup --from REPO` | Upgrade only from the given repos | `addUpgradeRepo()` + `resolvePool()`; "add already recommended" is switched off again | yes |
| `zypper install foo[=ver]` | Install or update exactly what was asked | install job for the chosen item, then `resolvePool()` | yes |
| `zypper list-updates` | Show what `zypper update` would do | runs **`doUpdate()`** itself | – |
| `zypper list-updates --all` | Show the highest available version of each installed package | `Selectable::highestAvailableVersionObj()`, **no solver** | – |
| `zypper list-patches` / `patch-check` | Show needed patches (`patch-check` also sets exit code 100/101) | establish status of patch items | – |

Code: `zypper/src/commands/update.cc` (`UpdateCmd::execute`),
`zypper/src/commands/patch.cc`, `zypper/src/SolverRequester.cc`
(`updatePatches`, `installPatch`), `zypper/src/solve-commit.cc`
(`solve_and_commit`, `dist_upgrade`, `set_solver_flags`), `zypper/src/update.cc`
(`find_updates`). The libzypp side is in
[04 §5](04-solver.md#5-modes) and [04 §19.4](04-solver.md#194-how-zypper-patch-builds-its-request).

### What all operations share

Every solver run goes through `SATResolver::solverInit()`
(`zypp/zypp/solver/detail/SATResolver.cc`), so these apply to **all**
operations, including `zypper update`:

* blacklist jobs for `retracted-patch-package()` and `ptf()` providers;
* locks;
* multiversion (NOOBSOLETES) jobs;
* requested-locale jobs;
* SystemCheck requirements;
* PTF protection when only `@System` is loaded (bsc#1203248).

The operations differ only in their **mode job**:

| Operation | Mode job |
|---|---|
| `zypper update` | `SOLVER_UPDATE` all |
| `zypper dist-upgrade` | `SOLVER_DISTUPGRADE` all |
| `zypper verify` | `SOLVER_VERIFY` all |
| `zypper patch`, `zypper install` | none, only explicit items |

They also differ in which flag set applies: `allow*` for normal operations,
`dupAllow*` for `dup` ([04 §14](04-solver.md#14-end-to-end-flag-and-job-reference)).

## 2. What each operation considers

| | `patch` | `update` | `dist-upgrade` | `install foo` |
|---|---|---|---|---|
| Unit of work | **patches** (only needed ones) | **packages** (all installed) | **whole system** | the named items |
| Packages not covered by any patch | not touched (unless `--with-update`) | updated | updated or replaced | only if named |
| Repo priority | through the patch's packages | respected | respected; the DUP repo set decides | respected |
| Vendor change | no (normal flags) | no (`solver.allowVendorChange`) | no (`solver.dupAllowVendorChange`, default false) | no |
| Downgrade | no | no | **yes** (`dupAllowDowngrade` default true) | no, unless an older version is named **and** `--oldpackage` (or `--force`) is given; otherwise zypper reports `SELECTED_IS_OLDER` (`SolverRequester::updateTo()`) |
| Arch change | no | no | **yes** (`dupAllowArchChange`) | no |
| Package renames (obsoletes) | yes | yes | yes | yes |
| Removes packages | only through conflicts or obsoletes (replacement) | only through conflicts or obsoletes (replacement, see libsolv `yumobs/split.t`) | **yes**: orphans with `--remove-orphaned`, orphaned packages in product droplists, plus conflicts/obsoletes | only through conflicts or obsoletes |
| Recommends of already installed packages | ignored | ignored | **added** (unless `--no-recommends`) | ignored |
| Blocked update | problem shown | **silently kept** | problem shown | problem shown |

Recommends handling: `set_ignore_recommends_of_installed()` in
`solve-commit.cc` ignores them for everything except `dup` (without
`--no-recommends`) and `inr`. Details:
[04 §18](04-solver.md#18-recommends-supplements-namespaces-and-rich-dependencies).

## 3. Behaviour matrix: special cases

The test repo had:

| Package | Installed | Available |
|---|---|---|
| `a` | 1 | 2; 3 is retracted |
| `b` | 2 (a retracted version; like in real metadata, only the repo copy carries the retracted marker) | 1; the retracted 2 |
| `c` | `1-1.ptf` (PTF package), required by the PTF master `ptf-1` | `c-2` (the official fix); a respin `ptf-1-2` of the master |
| `e` | 1 | 2, with an unresolvable require |
| `f` | 1 (vendor SUSE) | 2, from another vendor |
| `g` | 1 | 2 |

Patches: `patch:p-c` (conflicts `c < 2`) and `patch:p-g` (conflicts `g < 2`).

| Situation | `update` | `dist-upgrade` | `patch` | `install` (explicit) |
|---|---|---|---|---|
| **Newer retracted version available** (`a-3`), non-retracted `a-2` too | → `a-2`, `a-3` ignored | → `a-2` | only through patches, never to `a-3` | `zypper in a-3` (exact version) **installs it**: an explicit request lifts the blacklist |
| **Installed version is retracted** (`b-2`), the repo still has it, otherwise only older `b-1` | kept (no downgrade) | **kept**: the repo still contains an identical copy, and `solver_addduprules` doesn't consult the blacklist ([03a §B.2.3](03a-special-solvables.md#b23-installed-retracted-packages)) | not touched | `zypper in --oldpackage b-1` (without `--oldpackage`: `SELECTED_IS_OLDER`, nothing happens) |
| **Installed version is retracted, the repo dropped it** (only `b-1` left) *(separate run)* | kept | **downgraded** to `b-1` (`dupAllowDowngrade`) | not touched | as above |
| **Installed version is retracted, a newer non-retracted `b-3` exists** *(separate run)* | **updated** to `b-3` | **updated** to `b-3` | through a patch, if one covers it | `zypper in b-3` |
| **Retracted patch** | – | – | never offered: retracted patches are "not needed" (*code*, [03a §B.1.8](03a-special-solvables.md#b18-status-needed-applied-not-needed)) | **also skipped**: `zypper in patch:X` goes through `SolverRequester::installPatch()`, which only acts on broken (needed) patches, so it reports "not needed" |
| **PTF installed, official fix (`c-2`) available** | `c` **kept**; the PTF master pins it | **problem**: "ptf-1 requires c = 1-1.ptf". Solutions: remove the PTF, or keep `c` | a patch that conflicts with the PTF version is "needed", so `zypper patch` shows a **problem**. Solutions: skip the patch, or remove the PTF | `zypper in c=2` gives the same problem |
| **PTF respin available** (new `ptf-1` master) | **updated** to the respin. The blacklist on `ptf()` doesn't apply because an installed PTF has that name | updated | – | – |
| **Update blocked by dependencies** (`e-2`) | **silently kept**, no message | problem: "nothing provides …" | – (patch problems if a patch needs it) | problem |
| **Update only from another vendor** (`f-2`) | kept | **problem** ("problem with installed package f") unless `--allow-vendor-change` | – | `zypper in f` (name only): kept unless `--allow-vendor-change`. `zypper in f=2` selects that exact item (`setToInstall()`), so it replaces `f-1` **without** `--allow-vendor-change` (unless `f` is locked) |
| **Normal newer version** (`g-2`) | → `g-2` | → `g-2` | only if a needed patch covers it (`p-g`) | → `g-2` |

What to remember:

* **`zypper update` never complains.** A blocked package simply stays, and the
  summary lists it under "not updated" (`SHOW_NOT_UPDATED`). Use
  `zypper update foo` or `zypper install foo` to see *why*. This is also why the
  solver test case of a plain `up` rarely shows a problem.
* **Retracted means "not offered", not "pinned".** An installed retracted version
  is not removed *because* it is retracted, but it is not protected either: a
  newer non-retracted version replaces it on `update` and `dup`, and `dup`
  downgrades it if the repo no longer contains it. It stays only while the repo
  still has it and nothing newer exists. To leave it explicitly:
  `zypper in --oldpackage <older version>`.
* **A PTF blocks its packages until it is removed.** `update` keeps the PTF
  version without saying anything. `dup`, `patch` and `install` show a problem
  whose solution is to remove the PTF. The intended path is `zypper removeptf`
  ([03a §B.3](03a-special-solvables.md#b3-ptfs-program-temporary-fixes)).
* **A PTF respin is a normal update.** Only uninstalled PTFs are blocked from
  automatic installation.

## 4. zypper's patch policy on top of libzypp

These are zypper decisions, not libzypp's. File bugs about them against
zypper.

| Policy | Where | Behaviour |
|---|---|---|
| **Update stack first** | `SolverRequester::updatePatches()` | Pass 1 selects only needed patches with `restartSuggested()` ("affects the package manager"). Only if there are none does pass 2 select all needed patches. After patching the update stack, `zypper patch` must be run again |
| `--updatestack-only` | same | Stop after pass 1 |
| `--with-update` | `commands/patch.cc` | `setUpdateMode(true)`, so other packages are updated too. **Dropped** with a warning when pass 1 found update-stack patches. Implies `--with-optional` (bsc#1102261) |
| Optional patches | `exclude_optional_patches` in `zypper.conf` | Skipped unless `--with-optional` |
| Locked patches | `PoolItem::isUnwanted()` | A locked needed patch is skipped forever ([03a §B.1.8](03a-special-solvables.md#b18-status-needed-applied-not-needed)) |
| Interactive patches (`--skip-interactive`) | `Patch::interactiveWhenIgnoring()` | Patches with a message, license or reboot flag are skipped. A reboot flag is ignored if `reboot_req_non_interactive`; a license flag if `--auto-agree-with-licenses` |
| Filters `--category`, `--severity`, `--date`, `--bugzilla`, `--cve` | `CliMatchPatch` / `mark_updates_by_issue` | `--date` picks the newest patch version up to that date (bnc#919709) |
| Only "broken" (needed) patches are selected | `installPatch()` | Satisfied and not-relevant patches (including retracted ones) are never selected |

### Exit codes

| Code | Meaning | From |
|---|---|---|
| 100 | updates needed | `patch-check` only (`list-patches` returns 0) |
| 101 | security updates needed | `patch-check` only |
| 102 | reboot needed | after a commit that installed a reboot-flagged **patch** (zypper then also touches `/run/reboot-needed`, bsc#1217873); `zypper needs-rebooting` when that file exists. Packages that `isNeedreboot()` make libzypp touch the file during commit, but don't change zypper's exit code |
| 103 | restart of the package manager needed | after update-stack patches; run zypper again. 102 takes precedence over 103 |
| 104 | capability not found | `install` / `remove` |
| 106 | some repositories were skipped | any command that refreshes |
| 107 | an rpm `%post` script failed | commit |
| 8 | commit error (also after an interrupt during commit) | commit |

Definitions in `zypper/src/main.h`. Consumers such as `zypper migration` and
SUSE Manager rely on them ([14](14-consumers-and-api-surface.md)).

## 5. Which operation for which system

| System | Recommended | Why |
|---|---|---|
| **SLE** (and products with patches) | `zypper patch` | Patches are the supported unit: tested sets of packages with metadata (category, severity, reboot flags, retractions). It includes the update stack first |
| SLE, everything not covered by patches | `zypper patch --with-update` or `zypper update` | Packages without patches (e.g. from modules or third-party repos) are not touched by `patch` alone |
| **Tumbleweed** / rolling | `zypper dup` | There are no patches. `dup` synchronises the system with the repos: it downgrades, switches packages to the repo versions and can remove orphans. `update` only moves installed packages forward (renames and obsolete-based removals work in both, see §2) |
| **Leap** | `zypper patch` / `zypper update` within a release; `zypper dup` with a new `$releasever` between releases | |
| Major version / service pack change | `zypper migration` (SLE), `zypper dup` with switched repos | See [17](17-sle-migration.md) |

## 6. FAQ for triage

| Question in the bug | Answer | Owner |
|---|---|---|
| "`zypper patch` didn't update package X" | No needed patch covers X, or the patch is optional, locked, interactive (`--skip-interactive`) or filtered | expected; zypper policy |
| "`zypper up` didn't update X, no error shown" | The update is blocked (dependency, vendor, PTF). `doUpdate()` never reports problems. Ask for `zypper up X` or `zypper in X` output | expected; look at the real blocker |
| "`list-updates` shows X but `up` doesn't install it" | Only with `--all`, which ignores dependencies and policies; without it both use `doUpdate()` | expected |
| "`zypper patch` says it must run again" | Update stack patched first (exit 103, `solve-commit.cc`) | expected |
| "`zypper patch` wants to remove my PTF" | A newer official patch conflicts with the PTF version. Remove the PTF (`zypper removeptf`) or skip the patch | expected; the PTF is superseded |
| "Retracted version still installed" | Expected while the repo still contains it and nothing newer exists (`update`/`dup` keep it). A newer non-retracted version replaces it; to go back: `zypper in --oldpackage <older version>` | expected |
| "`dup` downgrades / changes vendor / arch" | `dupAllowDowngrade`/`ArchChange` default true; vendor change only with `--allow-vendor-change` or a relaxed product | expected; [04 §4.2](04-solver.md#42-flag-table) |
| "`dup` removed packages" | Product droplists or `--remove-orphaned` | expected; [17 §5](17-sle-migration.md#5-dup-features-that-exist-because-of-migrations) |
| "A patch is 'needed' but nothing installs" | The patch is locked, optional or interactive; or its packages are blocked (look for a problem) | depends |
| "A patch shows as 'not needed' although old packages are installed" | The fixing packages are from another vendor ([03a §B.1.10](03a-special-solvables.md#b110-establish-vs-vendor-why-a-patch-is-not-needed-although-old-packages-are-installed)) or the patch is retracted | expected |

## 7. Pitfalls & special cases

* **`zypper update` is `doUpdate()`,** a separate solver path: it ignores
  selections, `addRequire`/`addConflict` and upgrade repos, and reports **no
  problems** ([04 §5.2](04-solver.md#52-doupdate-update-to-newest-quietly)).
* **`zypper patch` installs patches, not "updates".** Packages without patches
  are left alone unless `--with-update`.
* **`--with-update` is silently dropped** in the update-stack pass (a warning is
  printed).
* **`list-updates --all` doesn't run the solver.** It can list versions nothing
  will ever install.
* **Explicit requests lift blacklisting**: an exact version of a retracted
  package can be installed with `zypper install` (zypper selects that exact
  item). If the name is locked, zypper uses `addRequire()` instead, which does
  **not** lift the blacklist. A downgrade also needs `--oldpackage`.
* **An installed blacklisted package exempts its whole name** from the
  blacklist. This is how PTF respins are handled (`ptf()` is a real rpm
  provide). It does **not** apply to retracted packages: the retracted marker is
  only on the repo copy, so the installed package never matches the blacklist
  job.
* **A PTF makes `update` keep its packages silently,** while `patch`/`dup`/
  `install` raise a problem.
* **`dup` uses different flags** (`dupAllow*`) than all other operations
  (`allow*`). A vendor-change setting in one doesn't affect the other.
* **`dup --from` is not a full DUP.** It uses `resolvePool()` with upgrade repos
  and switches "add already recommended" off again.

## 8. Where to start when debugging

1. Get the exact command line: the first lines of the run in `zypper.log`
   ([02 §3](02-core-infrastructure.md#3-logging)).
2. For "not updated" reports: ask the user to run `zypper in <pkg>` or
   `zypper up <pkg>`. These go through `resolvePool()` and show the problem
   that `zypper up` hides.
3. For patch questions: `zypper lp -a` / `zypper info -t patch <id>` (status,
   flags, retracted). Check whether the patch is locked (`zypper ll`).
4. Check for PTFs: `rpm -q --whatprovides 'ptf()'` (installed PTF masters).
5. Get a solver testcase (`--debug-solver`) and replay it
   ([11 §15](11-testing.md#15-bug-reproduction-workflow)). To compare the
   operations, change the job in the testcase (`update` / `distupgrade` /
   install) as in the crash course ([16](16-solver-crash-course.md)).
